# 延迟优化做了什么，哪些设备受益

这些改动既有公共管线优化，也有特定编码器优化。相同代码路径会在其它硬件上生效，但收益取决于实际后端，不能把 AMD 的实测数字套到 Intel 核显上。

| 改动 | 适用范围 | 作用 |
| --- | --- | --- |
| 采集与编码分开调度、只交付最新待处理画面 | 默认关闭的 DXGI 实验路径 | 验证独立采集线程和资源所有权；有平台前提，尚未作为公共默认启用 |
| Windows GPU 捕获表面直接交给硬件编码，按后端选择转换路径 | 支持相应 GPU 表面的 Windows 编码器 | 减少显存读回、CPU 转色和重新上传；实际回退路径以日志为准 |
| AMF 输入表面复用 | AMD AMF | 等编码器释放后复用转换资源，减少逐帧分配；不影响 Intel MFT/VPL |
| 解码表面租约、最新帧邮箱和 D3D11/WGL 共享 | 支持共享的 Windows 解码及显示驱动 | 避免解码后逐帧读回、CPU 转色和重新上传；租约防止画面被提前覆盖 |
| 按 DPI 缓存字库纹理 | 使用 Glow 的客户端 | 多屏缩放不同时跳过重复字库转换与上传，与远端编码器无关 |

因此，Intel 核显能使用适用的 GPU 路径、最新帧邮箱和客户端优化；AMD 的 AMF 池不会在 Intel 上运行。独立采集线程仍是默认关闭的实验，不是所有硬件都已启用的优化。硬件不支持共享时仍使用兼容路径，不能仅凭选择“硬件编码”就认定全程没有读回。

## 已确认的范围

一组 AMD AV1、4K60、40 Mbps 实验中，从采集画面就绪到发送端取走编码结果的平均耗时约从 **6.26–6.38 ms 降至 5.58 ms**，局部改善约 **11%–13%**。它包括准备、编码输出等待和交付，既不是纯 GPU 编码时间，也不是输入到屏幕的总延迟。60 秒验证仍出现重传请求和显示跳帧，不能据此宣称长时间稳定性达标。

客户端混合 DPI 字库缓存有独立的[定位、对照和测量记录](mixed-dpi-render-latency.md)。这些结果来自不同测试，不能把降幅相加。

忙轮询、缩小 AV1 输入队列、WLAN 提示、按流 QoS 和独立 UDP I/O 等实验没有满足收益或稳定性门槛，未作为默认优化启用；一帧 VBV 也未完成有效性能对照。实验工具和诊断计时的增加不等于产品性能改善。

## 后续还有哪些方向

- **输入与呈现分离**：避免显示驱动等待拖住输入发送，分别测输入队列和呈现队列。
- **解码到显示的同步**：减少 D3D/WGL 资源归还等待，评估平台原生呈现路径；保持颜色、HDR 和表面生命周期正确。
- **编码输出等待**：分别验证 Intel、AMD 等后端的提交、输出和码率策略，单变量对照，不照搬参数。
- **网络偶发停顿**：沿发送、收包、组帧和解码边界定位，再验证机制；不以平均延迟掩盖长尾。
- **稳定性与实际显示测量**：同条件长测、重连和资源释放检查，另测输入到可见画面的延迟，避免将 HUD 阶段均值当作端到端结果。

这些是待验证方向，不是已实现或已确认的收益。
