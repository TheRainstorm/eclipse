# R0 主机测量首批验证

日期：2026-10-24；版本：v0.18.8 开发测试版。本报告验证测量功能与有限条件下的开销，不证明真实串流延迟已经降低。[方案范围](../streaming-latency-and-stability-plan.md)、[事件及复现方法](../frame-tracing.md)。

## 已完成

- 主机本地 monotonic 事件与源 QPC 信息分开，输入和输出按 PTS 对应；编码后输出、发送出队及首尾 RTP API 返回可关联。
- 有界环形轨迹、分位数、窗口与溢出计数；遥测独立协商并使用无序、短寿命数据通道。
- Windows 只读实际采集源身份验证；生成源加密原生自环、禁用遥测与报告工具验证。

## 开销对照

环境：Linux x86_64，AMD Ryzen 5 5600G，12 个逻辑 CPU，glibc 2.39，Rust 1.95.0。使用 release 构建；生成图案 320×180、H.264、SDR、显式 OpenH264 软件编码与软件解码、2,000 kbps 目标、120 FPS 目标，localhost 原生加密链路，无音频、真实桌面输入或显示呈现。每次都记录实际解码后端 `openh264 (software, in-process)`，此组实验没有使用 GPU 编解码。

先登记门槛：稳态 FPS 中位数下降不超过 1%，发布间隔 p99 的中位数增加不超过 0.5 ms。随后运行三轮 ABBA，共 12 个独立进程、每次 600 帧；首秒预热排除在发布间隔统计之外。发布间隔由解码后 mailbox 的通知直接记录，不使用观察者轮询间隔。

| 指标 | 遥测关闭（6 次） | 遥测开启（6 次） |
|---|---:|---:|
| 解码总数 | 3,600 | 3,600 |
| 稳态 FPS 中位数 | 120.0013 | 120.0015 |
| 发布间隔 p99 的中位数 | 8.6522 ms | 8.6697 ms |
| 每次运行编码调用均值的中位数 | 0.4654 ms | 0.4643 ms |
| 解码后显示跳过计数总和 | 0 | 0 |

吞吐变化约 +0.0001%，发布间隔 p99 中位数差约 +0.0174 ms，通过本实验预先登记的门槛。该差值不应解释成测量模块固定增加的成本，也不能将软件低分辨率编码值与 4K HDR 硬编截图直接比较。采集调用包含生成器的节奏等待，不能解释成真实桌面采集效率。

Windows 控制台的独立只读静态桌面 probe 采样 60 次：2 次新源图像、58 次重复，保持 GPU 存储，源序号及 QPC 年龄符合预期。这验证源身份语义，不代表动态桌面吞吐或 Windows 遥测 A/B 已通过。

## 检查与边界

Linux 采集 16 项和 core 260 项回归通过（core 另有 1 项忽略），轨迹专项 5 项与报告工具 2 项通过。Linux / Windows 工作区所有目标编译检查通过。收尾增加旧回调竞争、乱序、跨 epoch 和 generation 退回校验，再次通过实际加密连接与 Windows 核心所有目标检查；新主机报告可到达客户端，旧控制统计继续有效。

尚未完成：真实 4K HDR / 高帧率主机基线、Windows 遥测开销对照、客户端 AU→解码→呈现的同帧事件、GPU 完成测量、适配器及驱动有效参数读回、Present/实际显示关联，以及长测。AMF 正式转换池、异步采集编码、呈现重构和 R1–R8 其余工作没有包含在本批中。

下一步先补齐目标硬件的同条件基线及客户端对应事件，再依据转换/驱动/发送/呈现等待的归属，交付能够证明收益的优化；不因测试版已生成而跳过性能门槛。
