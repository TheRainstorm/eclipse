# 输入时间线与原生重复呈现

本轮在正式版之后的开发提交中补充输入时间线，并修正两处视频交付行为。以下是受控生成源在真实 Windows 串流中的结果，仍需日常桌面和游戏验收。

## 统计起点决定能回答的问题

`Est.Total` 是已知视频阶段的独立窗口估计，`Video` 从源图像更新开始，两者都没有覆盖用户操作之前的输入路径。新增 `Input→Frame` 从同一次实际输入的客户端入队开始，关联主机接收、成功注入，以及注入后已观测源图像的首显回执；不会把输入确认 RTT 与视频均值相加。

这仍不能识别任意游戏是否已消费输入。其它桌面动画也会产生源更新；鼠标硬件采样、操作系统投递到客户端入队之前的等待，以及物理发光均未覆盖。“视觉响应”因此保留未知。详情和粉色曲线保留显示区间误差，送达的中点波动与校时误差分开。完整定义见[HUD](../hud.md)和[原生延迟](../native-latency.md)。

## 两处独立修正

- `f101dbaab9e3`：GPU/平面解码图像不再等待压缩队列排空才发布。压缩参考帧照常全部解码，每次解码调用仍只发布最后一张；需要同步 RGBA 转换时仍合并突发图像。增加批内替换和转换合并计数，便于区分跳过原因。
- `4906de1c4905`：鼠标事件继续唤醒并处理输入；视频导出所有者和生产 fence、几何、远端光标、输出颜色、VSync 及完整 UI 图层都未变化时，复用成功提交的合成结果。只比较导出 ID 会错过同一纹理里的新画面，必须包含生产 fence。光标形状到达而位置修订不变时也必须重新呈现。

复用路径不读取 GPU、不增加消费 fence、不调用 Present 或统计查询，也不生成显示回执。实际 Present 返回错误或遮挡状态时重试；`S_OK` 本身也不证明物理显示。返回状态定义见[Microsoft Present 文档](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgiswapchain-present)。

## 固定窗口的 ABBA 对照

发送端为 AMD AMF Balanced，接收端为 Intel Arc D3D11 硬解；固定 3840×2160@165 AV1 SDR、73 Mbps 请求、关闭 VSync、自有 GPU 源和持续鼠标移动。窗口工作区为 3840×2088，每轮持续检查相同物理几何，使用稳定后的 8.5–19 秒；源实际约 164.9 FPS。A 为 `bcc101574115`，B 为 `4906de1c4905`，两者都已有解码交付修正和新版 HUD。一次存在窗口位置漂移的前置对照已排除。

| 轮次 | Present 次数/秒 | 新图像提交/秒 | Present 调用墙钟 ms/秒 |
| --- | ---: | ---: | ---: |
| A1 | 325.4 | 161.2 | 575.5 |
| B1 | 164.8 | 163.9 | 52.9 |
| B2 | 165.0 | 164.1 | 74.5 |
| A2 | 344.9 | 162.6 | 563.5 |

墙钟包含驱动等待和线程调度，不能解读为 CPU 利用率或 GPU 执行时间。四轮原始呈现日志均正常闭合、无观测丢失；几何和生成源保持一致。结果证明大量重复提交已消除，同时保留了新图像提交。

相同轮次的短窗 Video 均值估测，A 为 17.2–18.2 ms，B 为 15.5–16.4 ms；Input→Frame 则分别为 20.8–23.9 ms 和 20.1–23.6 ms。它们带有数毫秒区间误差，样本窗口还可能重叠，因此不能把中心值差异宣称为精确的物理输入延迟下降，也不能宣称所有卡顿均已解决。

## 光标为何可能比视频统计更显慢

被测输出的独立光标通道没有位置或形状。仅凭缺失不能判断原因；随后在自有纯色区域的三个位置交替放置光标，检查 24 张解码图像中的 72 个小区域：箭头亮像素每次只出现在当前目标，独立通道仍没有位置或形状。这确认该输出的光标已经包含在视频里，必须经过视频采集、编码和显示路径。

这种行为符合[Desktop Duplication 的两种指针形式](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api#updating-the-desktop-pointer)：独立指针与已经绘入桌面的指针。另一条连接即使 Video 数值更高，若具有独立指针，光标仍可能更及时；这属于待对照验证的解释，不能仅按 Video 数值给交互体验排序。在客户端额外画一个指针不能消除视频里的原指针或应用响应延迟。

## 60 / 30 FPS 的额外等待与估测偏高

另两次固定为 1920×1080 AV1 SDR、12 Mbps，生成源仍为 165 FPS，只改变串流目标。以下是各次稳定后的三个短窗样本范围，并非统计置信区间。

| 串流目标 | 注入后后继源等待均值 | Video 均值估测 | Input→Frame 均值估测 | Input→Frame 均值区间半宽 |
| --- | ---: | ---: | ---: | ---: |
| 60 FPS | 7.26–10.45 ms | 16.83–18.08 ms | 26.60–29.18 ms | ±8.07–8.45 ms |
| 30 FPS | 16.86–23.50 ms | 29.00–29.49 ms | 48.00–55.13 ms | ±16.03–16.77 ms |

降低帧率确实增加了注入后等待后继画面的时间。没有把 `1000/FPS` 人为加到 E2E；帧节拍已经通过实际采样时刻影响结果。Video 的起点晚于输入，所以只有它仍看不到前面这部分等待。

另一个影响来自显示观测：复用未变化合成后不发起新统计查询，低帧率的回执区间随查询间隔变宽，中点可能高于实际显示时间。因此不能把表中 Input→Frame 的全部增量都当成真实响应变慢，更不能把不同样本总体的均值相减称为精确阶段耗时。区间、后继源等待和原有阶段值应一起看；该结果也不等于游戏的视觉响应时间。
