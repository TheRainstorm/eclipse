# 键盘捕获与所有权

系统键捕获是整个输入路径的状态，不逐一注册 Windows 快捷键。串流全屏、画面获得输入焦点、允许控制、关闭菜单且设置启用时，Windows 低级键盘钩子将所有按键交给远端，并阻止本机继续处理。同一规则覆盖 Win 单键、Win+Shift+方向键、Alt+Tab 等组合；客户端 Ctrl+左 Alt 控制命令独立保留。退出捕获不转移已经按下的键的所有权，其抬起仍由原路径处理。

连接串流和进入全屏会主动请求远端输入。菜单、设置、显示器选择、仅观看、控制通道暂不可用和窗口失焦只暂停实际捕获，保持用户的输入意图；阻塞解除后自动恢复。鼠标悬停本地工具栏只影响指针，不取消键盘捕获。Ctrl+Alt+Z 显式释放会保持释放，直到再次按快捷键、点击远端画面或进入全屏。退出全屏只关闭系统键捕获，普通远端文字和鼠标输入继续可用。“窗口”菜单的全屏入口与 Ctrl+Alt+F/X 调用同一个串流全屏操作；标题栏最大化按钮单独负责最大化/还原。

Ctrl+Alt+F/X 属于当前客户端的本地命令。Ctrl/Alt 按下时可能已发送远端，识别命令后释放远端按键，F/X 本身不发送，避免两端同时切换全屏。输入发送错误或队列溢出会保持释放，作为无法继续可靠传输输入时的故障处理；不会自动重新抢占。

未捕获时，Windows 负责本机系统快捷键。普通窗口消息继续传输文字与常规按键，但不把已经交给 Windows 的 Win 键及其组合再次发送到远端。客户端不模拟本机跨屏快捷键、不注入掩盖开始菜单的假按键。Ctrl+Alt+Del 属于 Windows 安全注意序列，不由普通客户端钩子捕获。

低级钩子在独立线程安装并运行消息循环，保存物理修饰键及按键所有权。它只做有限队列写入和异步窗口通知；不执行渲染、网络发送或等待 GUI 锁。渲染线程收到通知后请求重绘、排出输入队列。来自外层远程桌面或辅助工具的 injected 按键也按同样规则处理，不整体过滤。

## 参考实现

- [Moonlight 输入管理](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/streaming/input/input.cpp)：`updateKeyboardGrabState()` 根据捕获模式、输入捕获与全屏状态调用 SDL 键盘 grab；`isSystemKeyCaptureActive()` 还要求输入焦点。本项目参考状态管理方式，未复制其 GPL 实现。
- [SDL 键盘 grab API](https://wiki.libsdl.org/SDL2/SDL_SetWindowKeyboardGrab)：由平台捕获层处理系统组合键。
- [微软 LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc)：回调在安装线程执行，超时可能静默移除，建议使用独立线程；回调时异步按键状态尚未更新。
- [uu-remote-linux](https://github.com/VallierDev/uu-remote-linux)：当前检查的 Rust 主体以被控端采集、注入和协议为主，不包含可直接移植的 Windows 客户端系统键捕获实现。

## 验证边界

窗口消息使用 `GetKeyState` 获取消息生成时的修饰键状态，避免钩子线程提前处理后续按键后把旧字母误认成本地快捷键。系统捕获激活时，窗口消息与钩子遵循同一远端归属，包含没有经过低级钩子的窗口输入；发送边界去重修饰键状态转换。释放捕获后，窗口层继续保持 Win 及其组合归本机。窗口消息处理不能替代低级钩子对 Windows shell 的拦截。

捕获意图回归覆盖进入与退出全屏、菜单关闭、失焦恢复、临时断控、仅观看和显式释放；临时暂停不重写用户意图。状态回归覆盖全部 255 个虚拟键、左右 Win 及多键组合、释放顺序、模式切换、AltGr 和本地控制命令。Windows 独立测试在新建的非交互窗口站安装真实钩子，验证 GUI 线程不泵消息时钩子线程仍能处理消息，以及正常卸载。它不向工作桌面注入输入，不能替代真实桌面上开始菜单与远端窗口的交互验收。

嵌套客户端的快捷键透传是另一个独立功能；当前没有 F12 切换快捷键表。外层客户端若先截获组合键，内层无法补收它，需要在外层释放捕获或使用其透传功能。

## 长按与释放

每个会话只释放自己已经转发且尚未抬起的键，忽略重复或未拥有的抬起。清理时先释放普通键，再释放修饰键；不广播额外的 Win/Alt/Ctrl/Shift 抬起。同一远端输入仍然可用时，改变系统捕获方式不会单独触发按键清理。失焦、显式释放和断开等真正结束输入的操作仍会清理，避免卡键。

UU 被控端不会自行维持长按：若按住期间只收到首次 `kbd_press`，会在约 150–300ms 后把按键当作短按释放。普通键转发 Windows typematic 产生的重复 `kbd_press`；Windows 对 Alt 等修饰键的重复并不可靠，且在 Alt+Tab 等组合后可能停止，因此客户端为仍按住的修饰键使用一个统一的 30ms 刷新计时器。真实抬起时只发送一次 `kbd_release`。Windows 钩子截获重复事件且不交还本机；诊断只记录转发次数，不记录文字或普通按键序列。

这与 Moonlight/Sunshine 的分工不同。Moonlight 客户端忽略 `repeat` 事件，只发送状态变化；Sunshine 被控端的 `repeat_key()` 自己按约 500ms 首次延迟、约 40ms 周期生成重复。uu-remote-linux 的 viewer 同样只处理 `repeat:false` 且没有修饰键刷新计时器，因此它不能作为 UU 官方宿主会自行维持长按的依据。UU 官方客户端在本机输入流只有单次 Alt 按下时，仍会让官方宿主收到约 30ms 的 Alt 重复；兼容客户端必须按此行为发送修饰键刷新。

诊断区分捕获请求与真实钩子活动，记录窗口有效性、前台/桌面匹配、回调与放行的汇总计数。发生应用级按键清理时记录代码调用位置、按住键数量及 Win/Alt 是否处于按住状态；不记录键入文字或普通按键序列。
