# 键盘捕获与所有权

系统键捕获是整个输入路径的状态，不逐一注册 Windows 快捷键。串流全屏、画面获得输入焦点、允许控制、关闭菜单且设置启用时，Windows 低级键盘钩子将所有按键交给远端，并阻止本机继续处理。同一规则覆盖 Win 单键、Win+Shift+方向键、Alt+Tab 等组合；客户端 Ctrl+左 Alt 控制命令独立保留。退出捕获不转移已经按下的键的所有权，其抬起仍由原路径处理。

连接串流和进入全屏会主动请求远端输入。菜单、设置、显示器选择、仅观看、控制通道暂不可用和窗口失焦只暂停实际捕获，保持用户的输入意图；阻塞解除后自动恢复。鼠标悬停本地工具栏只影响指针，不取消键盘捕获。Ctrl+Alt+Z 显式释放会保持释放，直到再次按快捷键、点击远端画面或进入全屏。退出全屏只关闭系统键捕获，普通远端文字和鼠标输入继续可用。“窗口”菜单的全屏入口与 Ctrl+Alt+F/X 调用同一个串流全屏操作；标题栏最大化按钮单独负责最大化/还原。

Ctrl+Alt+F/X 属于当前客户端的本地命令。Ctrl/Alt 按下时可能已发送远端，识别命令后释放远端按键，F/X 本身不发送，避免两端同时切换全屏。输入发送错误或队列溢出会保持释放，作为无法继续可靠传输输入时的故障处理；不会自动重新抢占。

未捕获时，Windows 负责本机系统快捷键。普通窗口消息继续传输文字与常规按键，但不把已经交给 Windows 的 Win 键及其组合再次发送到远端。系统捕获活动时，Win 组合键必须整条属于远端，不能因 `GetAsyncKeyState` 的时序竞态把 Win 按下交给本机而把后续字母交给远端；Win+V、Win+Shift+方向键等因此不再混合触发本机开始菜单和远端操作。客户端不模拟本机跨屏快捷键、不注入掩盖开始菜单的假按键。Ctrl+Alt+Del 属于 Windows 安全注意序列，不由普通客户端钩子捕获。

Windows 初始化时移除 winit 默认注册的键盘 Raw Input，键盘统一由窗口消息和低级钩子处理；鼠标 Raw Input 的注册目标和标志保留，供相对移动使用。前台 Raw Input 键盘注册与低级钩子并存可能导致实体键盘绕过钩子，窗口仍收到按键而系统组合键未被拦截。客户端不消费原始键盘设备事件，因此在安装钩子、显示窗口之前一次性去掉这条多余路径，不依赖等待、反复切全屏或重装钩子。注册修改按 [RegisterRawInputDevices](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerrawinputdevices) 的进程级设备类别规则执行，只移除 Keyboard usage；失败时不将系统捕获报告为可用。

低级钩子在独立线程安装并运行消息循环，保存物理修饰键及按键所有权。它只做有限队列写入和异步窗口通知；不执行渲染、网络发送或等待 GUI 锁。渲染线程收到通知后请求重绘、排出输入队列。来自外层远程桌面或辅助工具的 injected 按键也按同样规则处理，不整体过滤。

## 参考实现

- [Moonlight 输入管理](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/streaming/input/input.cpp)：`updateKeyboardGrabState()` 根据捕获模式、输入捕获与全屏状态调用 SDL 键盘 grab；`isSystemKeyCaptureActive()` 还要求输入焦点。本项目参考状态管理方式，未复制其 GPL 实现。
- [SDL 键盘 grab API](https://wiki.libsdl.org/SDL2/SDL_SetWindowKeyboardGrab)：由平台捕获层处理系统组合键。
- [微软 LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc)：回调在安装线程执行，超时可能静默移除，建议使用独立线程；回调时异步按键状态尚未更新。
- [uu-remote-linux](https://github.com/VallierDev/uu-remote-linux)：当前检查的 Rust 主体以被控端采集、注入和协议为主，不包含可直接移植的 Windows 客户端系统键捕获实现。

## 验证边界

窗口消息使用 `GetKeyState` 获取消息生成时的修饰键状态，避免钩子线程提前处理后续按键后把旧字母误认成本地快捷键。系统捕获激活时，窗口消息与钩子遵循同一远端归属，包含没有经过低级钩子的窗口输入；发送边界去重修饰键状态转换。释放捕获后，窗口层继续保持 Win 及其组合归本机。窗口消息处理不能替代低级钩子对 Windows shell 的拦截。

捕获意图回归覆盖进入与退出全屏、菜单关闭、失焦恢复、临时断控、仅观看和显式释放；临时暂停不重写用户意图。状态回归覆盖全部 255 个虚拟键、左右 Win 及多键组合、释放顺序、模式切换、AltGr 和本地控制命令。Windows 独立测试在新建的非交互窗口站安装真实钩子，验证生产初始化移除键盘 Raw Input、保留鼠标目标与标志、重复初始化安全，以及 GUI 线程不泵消息时钩子线程仍能处理消息和正常卸载。它不向工作桌面注入输入，不能替代真实桌面上开始菜单与远端窗口的交互验收。

嵌套客户端的快捷键透传由 Ctrl+Alt+F12 切换。关闭透传时，Ctrl+Alt+F/Q/S/M/H/Z/P/C/X 等属于当前客户端命令；开启后，除 F12 外的 Ctrl+Alt 组合发送到远端，F12 仍由当前客户端处理，避免无法退出透传。该状态随客户端配置保存，也可在串流设置和串流菜单中查看。外层客户端若先截获组合键，内层无法补收它；需要在外层开启透传或释放捕获。

## 长按与释放

每个会话只释放自己已经转发且尚未抬起的键，忽略重复或未拥有的抬起。清理时先释放普通键，再释放修饰键；不广播额外的 Win/Alt/Ctrl/Shift 抬起。同一远端输入仍然可用时，改变系统捕获方式不会单独触发按键清理。失焦、显式释放和断开等真正结束输入的操作仍会清理，避免卡键。

UU 被控端不会自行维持长按：若按住期间只收到首次 `kbd_press`，会在约 150–300ms 后把按键当作短按释放。普通键转发 Windows typematic 产生的重复 `kbd_press`；Windows 对 Alt 等修饰键的重复并不可靠，且在 Alt+Tab 等组合后可能停止，因此客户端为仍按住的修饰键使用一个统一的 30ms 刷新计时器。真实抬起时只发送一次 `kbd_release`。Windows 钩子截获重复事件且不交还本机；诊断只记录转发次数，不记录文字或普通按键序列。

这与 Moonlight/Sunshine 的分工不同。Moonlight 客户端忽略 `repeat` 事件，只发送状态变化；Sunshine 被控端的 `repeat_key()` 自己按约 500ms 首次延迟、约 40ms 周期生成重复。uu-remote-linux 的 viewer 同样只处理 `repeat:false` 且没有修饰键刷新计时器，因此它不能作为 UU 官方宿主会自行维持长按的依据。UU 官方客户端在本机输入流只有单次 Alt 按下时，仍会让官方宿主收到约 30ms 的 Alt 重复；兼容客户端必须按此行为发送修饰键刷新。

诊断区分捕获请求与真实钩子活动，记录窗口有效性、前台/桌面匹配、回调与放行的汇总计数。发生应用级按键清理时记录代码调用位置、按住键数量及 Win/Alt 是否处于按住状态；不记录键入文字或普通按键序列。

Windows 诊断还每 250ms 向独立钩子线程发送异步消息泵探针，记录发送、确认、延迟、回调起止时间及最长耗时（包括放行时的下游钩子）。线程存活和探针确认只证明消息泵能工作，不能证明 Windows 仍保留钩子或每次输入都经过它。窗口输入来源按硬件、注入、系统及未知汇总；Tab 只计数，不记录普通按键序列。来源取自 [GetCurrentInputMessageSource](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getcurrentinputmessagesource)，不可据此认定具体输入设备或软件。[LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc) 的调用线程及超时语义决定了这些指标需要分开观察。诊断不重装钩子、不注入按键，文件写入仍在钩子之外。

## 首次全屏 Alt+Tab / Win 捕获延迟复盘（2026-10-22）

**结果：修复版 `4be60a8` 经用户实体键盘实机确认，首次全屏捕获问题已解决。** 生产修复为 `031de2d`，`4be60a8` 修正了原生回归测试中的系统查询假设。

### 现象与影响

串流刚进入全屏时，Alt+Tab 或 Win 仍由本机响应；有时要等待十几秒、反复切换窗口后才能正常交给远端。失败并非每次发生，同一版本也有首次即正常的会话。串流已经出画面、控制通道已就绪、窗口已获前台且捕获开关为真，仍可能发生，因此连接成功和捕获状态为真都不足以证明系统键已被拦截。

### 定位过程与关键证据

最初检查了输入就绪、窗口激活、捕获意图与失焦恢复，并恢复窗口消息的统一输入归属。这些路径的状态测试通过后，用户仍反馈实体 Alt+Tab 失败。窗口消息可以补收普通按键，却不能阻止 Windows shell 先执行系统快捷键。

进一步记录低级钩子的回调计数、窗口输入来源、前台归属，以及独立钩子线程的消息泵探针，得到以下证据：

| 观察 | 定位意义 |
| --- | --- |
| 全屏且前台匹配时，窗口收到硬件来源的 Alt，低级钩子却没有对应回调，随后本机窗口获前台 | 事件绕过钩子，不能只检查应用层是否把 Alt 发给远端 |
| 失败期间，切到后台后钩子计数增加；回到前台又停止，窗口硬件输入计数继续增加 | 问题与前台输入路径相关，不能简单归因于钩子永久失效 |
| 消息泵探针持续得到确认，所查失败样本延迟约 0–1ms、最长已完成回调约 13ms | 这些样本不支持消息泵停顿导致此次故障的解释 |
| 一次会话约 27 秒才首次在前台截获，另一会话首次即成功 | 不存在可据此采用的固定启动等待时间 |

某个样本约 70 秒才出现前台捕获，但中间没有连续尝试的证据，不能描述为“持续尝试 70 秒才恢复”。诊断保留事件路径和计数，不记录普通键入内容。

### 原因与修复

检查框架的实际注册行为发现：[winit 的事件循环初始化](../vendor/winit/src/platform_impl/windows/event_loop.rs) 默认调用 `register_all_mice_and_keyboards_for_raw_input()`，将鼠标和键盘都注册为前台 Raw Input；本项目使用的 eframe 0.29.1 `device_event()` 只消费 `MouseMotion`，不消费原始键盘事件。客户端同时保留了一条多余的 Raw Input 键盘路径和一条负责系统键拦截的低级钩子路径。

失败样本表现为前台 Raw Input 键盘注册与低级钩子并存时，实体键盘绕过钩子。移除该注册后用户确认故障消失，支持这是本次问题的原因。具体为何在等待或切换窗口后偶尔恢复，没有进一步证明；这也不是对所有 Windows 版本、所有 Raw Input 与钩子组合行为的普遍断言。

[生产初始化代码](../crates/uu-gui/src/platform.rs) 在安装低级钩子、显示窗口之前，对 Generic Desktop / Keyboard（Usage Page `0x01`、Usage `0x06`）调用 `RegisterRawInputDevices`，使用 `RIDEV_REMOVE` 和空目标窗口，移除本进程的原始键盘注册。鼠标注册保留，继续提供相对移动。移除失败时记录错误，不将系统捕获报告为可用。

这项配置在初始化阶段完成，键盘继续由窗口消息与独立线程的低级钩子共同处理。全屏、失焦、释放捕获及按住时切换模式沿用统一的按键所有权规则；无需为 Alt+Tab、Win 分别补丁，也无需延时启用、定时重装钩子或注入额外按键。

### 验证与测试修正

- Linux GUI 95 项通过；Windows GNU 含测试的交叉编译检查通过。
- 最终 Windows 原生 GUI 96 项通过，覆盖输入状态转换、全屏进出、失焦、按住时切换模式和抬起等已有回归。
- 独立非交互窗口站测试 1 项通过：先建立与 winit 一致的鼠标及键盘注册，再调用生产初始化，查询确认键盘注册消失、鼠标目标与查询标志保持不变、重复移除安全，并验证钩子消息泵与卸载。
- 首版隔离测试错误地要求系统查询原样返回注册请求中的 `RIDEV_DEVNOTIFY`，实际读回为 0。修正为比较操作前后的系统读回值，验证鼠标注册未被改变；原失败不属于键盘移除失败。
- Windows 原生包构建、120 帧合成音视频检查和安装文件校验通过。用户随后明确反馈“确实解决了”，完成本次实体键盘故障的实机验收；该反馈与自动化测试结果分别记录。
- 用户后来又从另一台Windows控制端复测，确认原先Win与Alt+Tab的问题均已修复。后续鼠标跟手优化单独跟踪，不将这一已确认的键盘问题重新标为待验收。

### 后续维护约束

升级 winit / eframe，或引入新的输入库时，应重新检查原始键盘注册及其真实消费者。尤其要注意后续调用 `listen_device_events()` 会重新注册设备，可能恢复已移除的键盘路径。确需原始键盘能力时，应重新设计它与系统键捕获的所有权关系，而不是直接恢复默认注册。

遇到类似问题，先区分“窗口收到输入”“低级钩子收到输入”“本机系统快捷键被阻止”三个事实。消息泵健康、状态测试通过或窗口已转发按键，都不能单独替代实体键盘的桌面交互验收。
