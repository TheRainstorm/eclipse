# 串流恢复与 SRTP 序号回绕

长稳测试曾发现：主机继续发送，声音仍在，视频却永久停止，解码错误计数为 0。这说明只看解码错误不足以判断串流正常，还需观察视频收包、解码和呈现是否持续增长。

项目使用的 SRTP 依赖原先以 100 个包作为序号回绕附近的判断范围，并在迟到重传时改写最后序号。RTP 序号是 16 位，反复经过 65535→0；回绕附近丢失超过 100 个包或出现迟到重传，可能使双方的回绕计数不一致，后续正常包持续无法通过认证。触发时机取决于初始序号、包速率和丢包，并非固定几分钟。

0.7的局部修复按最高已接受的扩展包索引判断回绕，旧包保留自己的索引并且不倒退最高状态；索引耗尽时报错。实现依据 [RFC 3711 §3.3.1](https://www.rfc-editor.org/rfc/rfc3711.html#section-3.3.1)，参考 [Pion 的最高索引管理](https://github.com/pion/srtp/blob/main/context.go)。加密算法、认证与重放保护保留。修复同时用于原生发送端和两种连接模式的接收端；旧版本仍使用旧依赖，原生模式建议两端一起升级。

接收循环也保留尚未完成的轨道读取，在修复事件或计时器到来时继续同一次读取，完成后才开始下一次。这遵循依赖的取消约束，避免无意丢弃读取中的数据。

验证包含两种支持的加密配置、迟到重传的密文一致性、跨回绕连续丢失 201 个包、篡改认证标签及重复包拒绝，并运行上游密码测试向量与会话测试。以下最小探针只使用合成数据，不建立网络连接：

```sh
cargo run --release -p uu-core --example srtp_retransmit_probe --locked
```

这解决的是已复现的回绕状态问题。普通网络中断、驱动停顿、队列积压和解码参考链损坏仍需分别诊断；视频 FEC 尚未实现。

后续开发版将解码 FPS 改为接收定时器按各轨道的实际解码增量采样。停止出帧后也会更新为 0，避免沿用停图前的帧率；解码耗时保留最近一次观测值。0.7.0 的旧统计逻辑尚不包含此项。
