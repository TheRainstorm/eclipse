# 串流恢复与 SRTP 序号回绕

长稳测试曾发现：主机继续发送，声音仍在，视频却永久停止，解码错误计数为 0。这说明只看解码错误不足以判断串流正常，还需观察视频收包、解码和呈现是否持续增长。

项目使用的 SRTP 依赖原先以 100 个包作为序号回绕附近的判断范围，并在迟到重传时改写最后序号。RTP 序号是 16 位，反复经过 65535→0；回绕附近丢失超过 100 个包或出现迟到重传，可能使双方的回绕计数不一致，后续正常包持续无法通过认证。触发时机取决于初始序号、包速率和丢包，并非固定几分钟。

0.7的局部修复按最高已接受的扩展包索引判断回绕，旧包保留自己的索引并且不倒退最高状态；索引耗尽时报错。实现依据 [RFC 3711 §3.3.1](https://www.rfc-editor.org/rfc/rfc3711.html#section-3.3.1)，参考 [Pion 的最高索引管理](https://github.com/pion/srtp/blob/main/context.go)。加密算法、认证与重放保护保留。修复同时用于原生发送端和两种连接模式的接收端；旧版本仍使用旧依赖，原生模式建议两端一起升级。

接收循环也保留尚未完成的轨道读取，在修复事件或计时器到来时继续同一次读取，完成后才开始下一次。这遵循依赖的取消约束，避免无意丢弃读取中的数据。

验证包含两种支持的加密配置、迟到重传的密文一致性、跨回绕连续丢失 201 个包、篡改认证标签及重复包拒绝，并运行上游密码测试向量与会话测试。以下最小探针只使用合成数据，不建立网络连接：

```sh
cargo run --release -p uu-core --example srtp_retransmit_probe --locked
```

这解决的是已复现的回绕状态问题。普通网络中断、驱动停顿、队列积压和解码参考链损坏仍需分别诊断；视频 FEC 尚未实现。

后续开发版将解码 FPS 改为接收定时器按各轨道的实际解码增量采样。停止出帧后也会更新为 0，避免沿用停图前的帧率；解码耗时保留最近一次观测值。0.7.0 的旧统计逻辑尚不包含此项。

## 媒体调试与画面数据

0.8起的 `UU_MEDIA_DEBUG=1` 只输出接收、解码和恢复诊断，不再周期性把解码画面保存到公共临时目录。0.7.0 及更早版本仍含旧行为；排障时应优先使用新版本。显式的 `UU_DUMP_H264` 是独立的码流导出选项，导出可能包含远端画面，只应在明确需要时使用并自行保管文件。

## 0.8：迟到补包与重放窗口

应用最多保留2048个RTP包用于重排，而SRTP依赖的默认重放窗口只有64。此前未曾收到的有效补包若已落后数百个序号，会在到达重排队列前被拒绝。两种模式现在显式选择2048包窗口，与原有队列上限一致；没有延长帧修复截止时间，也不为健康画面增加固定等待。[RFC 3711 §3.3.2](https://www.rfc-editor.org/rfc/rfc3711.html#section-3.3.2)允许使用更大的有界窗口。

验证同时发现，依赖原来的环绕检测器用归一化差值检查迟到包，却用原始序号相减标记它；首次迟到的上一轮包可能未被记录。SRTP选项改用有界环形位图，检查和记录使用相同年龄，只在认证成功后接受，不因认证失败移动窗口。默认64包和应用2048包窗口都验证了迟到包只接受一次；SRTCP选择、加密与认证算法保持原样。

新增仅监听本机的UDP测试中继，在SRTP解密前丢弃一个合成RTP包，让其落后300个新包，再通过真实加密RTCP NACK请求补发：旧配置无法交付有效补包，新配置成功。第一次篡改补包被拒绝，下一次有效补包只交付一次，再次重发仍被拒绝。两种加密配置还验证跨序号回绕、过期包拒绝和认证失败不占用序号；位图与完整包索引参考模型比较25万次可重复事件。测试不读取桌面、账号或输入设备，不修改系统网络。

接收层既有的故障注入发生在解密后，侧重坏帧与关键帧恢复；新的网络中继测试用于验证线上丢包、认证和NACK链路。NACK请求数不等于成功修复数，同一SSRC的补发也不一定计入独立RTX轨道统计。这些改进不是视频FEC，真实网络超过队列或恢复时间上限时仍需要新的关键帧。
