# v0.19：兼容官方 UU 手机客户端的可行性

评估日期：2026-10-24。结论：技术上可行，值得先做官方协议的被控端适配；目前本项目尚未实现这条连接路径，不能把“支持 UU 账号连接服务”理解为已经兼容官方手机客户端。

## 已有证据

`uu-remote-linux` 已独立实现官方被控端协议。其固定快照 `50ed54d77a9084d18797061650bed9f85293c421` 的作者报告了官方 Android 客户端编码与多屏操作实测，也报告了 iPhone 4.42.0 在特定 GNOME Portal 场景下的锁屏冷连接实测。这支持“第三方被控端可以与官方手机客户端互通”的判断；这些是参考项目的验收结果，不是本项目或 Windows 后台服务的验收结果。[参考项目说明](https://github.com/VallierDev/uu-remote-linux/blob/50ed54d77a9084d18797061650bed9f85293c421/README.md)

代码中还存在移动输入法文本输入、官方控制/文本通道、桌面初始化及锁屏状态等具体处理路径，说明兼容需要覆盖媒体以外的会话初始化和交互。[输入协议](https://github.com/VallierDev/uu-remote-linux/blob/50ed54d77a9084d18797061650bed9f85293c421/src/control_protocol.rs)、[会话实现](https://github.com/VallierDev/uu-remote-linux/blob/50ed54d77a9084d18797061650bed9f85293c421/src/webrtc.rs)

## 本项目当前的差距

目前原生被控入口要求 `device_bootstrap` 信令和 `eclipse-device-auth-v2` 数据通道，随后验证 Eclipse 公钥身份，再建立原生媒体会话。官方手机没有实现这个私有握手，因此不能直接连入。对应入口见 [设备启动握手](../crates/uu-core/src/device_channel.rs)、[互联网被控连接](../crates/uu-core/src/device_internet.rs) 和 [共享运行时](../crates/uu-core/src/host_runtime.rs)。

项目已有官方 Windows 被控端的控制端实现，包括部分 CONTROL、TEXT、媒体和信令解析。这些是可用基础；被控角色还需要反向实现初始化、状态应答和能力上报。消息能解析不等于具备完整服务行为。

| 层次 | 可以复用 | 仍需实现或验证 |
|---|---|---|
| 登录、设备与上线 | UU API、账号、设备注册、房间续约、信令心跳 | 官方手机识别的设备与能力字段、被控连接请求及会话路由 |
| 信令与传输 | Socket.IO、ICE、DTLS/SRTP、RTP、RTCP | 官方 offer/answer 封装、通道名称、音视频参数及媒体扩展；不能发送 Eclipse 私有启动握手 |
| 屏幕和编码 | Windows DXGI/D3D11、原生 AMF/Intel、Linux 采集与硬编 | 按官方请求选择格式、分辨率和帧率，正确回答初始化、切屏和关键帧请求 |
| 输入 | 当前会话输入所有权、Windows/Wayland 后端 | 官方按键和修饰键语义、绝对/相对指针、移动输入法文本、断开释放；不能直接套用 Eclipse HID 包 |
| 声音与剪贴板 | Opus 与系统音频、图文 OS 剪贴板后端 | 官方通道和能力协商；私有 PNG 分片协议不适用于官方手机 |
| 信任和权限 | 主机会话租约、输入权限、取消和管理模型 | 单独定义官方账号会话的准入规则；官方客户端没有 Eclipse 公钥凭据 |
| 手机附加工具 | 可以复用部分消息编解码和通用平台能力 | 文件传输、终端、端口映射、自动解锁等服务端 RPC；客户端有按钮不会自动补上被控功能 |

## 推荐的实现边界

在现有采集、编码、音频、输入后端外增加独立的官方协议会话适配器，复用统一的会话取消和权限检查。根据明确的入口策略分派到官方协议或 Eclipse 原生协议，不把“不认识的消息”降级为已授权连接。

官方兼容入口应默认关闭，开启时明确采用 UU 账号会话的授权策略。它不能伪装成完成了 Eclipse 公钥配对，也不能继承原生端的管理权限。账号准入、设备确认、输入与剪贴板权限需要分别落实。原生输入和本地管理员管道不能作为官方 RPC 的任意转发入口。

Windows 锁屏服务可复用其采集和输入能力。若后续增加终端或文件操作，应在当前被控用户的身份与文件权限下执行，不能因为媒体进程运行于 System 就把这些工具也做成 System 权限。自动解锁同样需要单独的操作系统实现和凭据生命周期，不能只返回一个成功状态。

兼容层先准确公布已经实现的能力。尚未实现的工具应不宣告支持，或给出明确的不支持响应。私有 FEC、图片剪贴板和远程管理仅在双方实际协商成功时启用，不能假定官方客户端理解它们。

## 分阶段验收

1. 使用生成画面验证官方账号设备发现、H.264 首帧、断开与重连。先固定一个公开记录版本的 Android 客户端，确认授权失败时没有采集或输入。
2. 验证基础鼠标、键盘、移动输入法、声音和文本剪贴板，包括失焦、取消、重连后的释放与内容隔离；再单独验证 iPhone。
3. 验证 HEVC/AV1 的真实协商、不同尺寸和帧率、多屏切换、关键帧恢复及受限网络，记录具体手机和驱动支持范围。
4. 按实际使用需求增加文件等附加 RPC，再处理各平台锁屏和自动解锁。每项独立验证，不因桌面已经出图就宣称手机全部功能兼容。

正式验收需要真实官方客户端；本地仿真协议和参考项目的测试不能替代。官方服务与客户端可以独立更新，兼容层需保留版本与协议形状回归，当前不能承诺未来所有版本都兼容。

## 路线与许可

| 路线 | 适用范围与代价 |
|---|---|
| 为本项目独立实现官方协议适配 | 可以保留现有 Windows 原生硬编、后台服务与统一后端；需要持续维护协议、授权和手机实机回归。建议作为后续实现路线。 |
| 独立部署参考项目 | 可用于 Linux 场景的先行验证；不是让本项目 Windows server 自动获得兼容能力，也不与现有配置、配对和发布流程天然合并。 |
| 自行开发手机 UI | 需要维护手机交互和平台工程；不符合本次“使用官方手机客户端”的目的。 |

参考项目使用 GPL-3.0，本项目使用 MIT OR Apache-2.0。本评估选择独立编写协议适配，不复制参考源码；若选择集成或分发参考实现，需要单独确定发布和许可方案，不能把进程隔离视为自动解决许可问题。[参考项目许可证](https://github.com/VallierDev/uu-remote-linux/blob/50ed54d77a9084d18797061650bed9f85293c421/LICENSE)
