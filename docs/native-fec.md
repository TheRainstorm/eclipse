# 原生视频 FEC

支持本项目两端的原生视频。双方 SDP 都确认 `xor1-8-20-s62` 后自动启用，旧端继续使用 NACK/RTX。H.264、HEVC、AV1 共用同一 RTP 保护路径；不改变 UU 官方兼容连接，也不宣称兼容 Sunshine、Moonlight 或标准 ULPFEC 的线上格式。

每个校验组包含同一画面内最多 8 个 RTP 包，通过 XOR 保护负载、长度、时间戳和帧尾标记。收到校验和其余数据后，可以立即重建其中缺失的一个包，送回原有有界重排与完整帧检查。原始 RTP 立即发送，不等组满或等待校验送达；画面末尾立即结束当前组。只有一个包的组不发校验，同一组丢失两包以上仍需 NACK/RTX 或关键帧恢复，因此当前实现不保证突发丢包恢复。

校验有独立信用预算：以视频编码负载为基数，校验内容与固定封装估算的附加预算不超过 20%，不足时跳过校验。编码码率仍表示视频编码目标，实际线路还包含校验、音频、IP 与加密封装；拥塞时需要调低客户端码率。发送队列最多 8 项，过期 10ms 的校验跳过，SCTP 积压时跳过，不阻塞采集和视频发送。校验通道无序、PR-SCTP 寿命 5ms；本项目使用的 webrtc-rs 会把 `max_retransmits=0` 当作默认可靠模式，因此使用明确的短寿命避免无限重传。

校验与原始 RTP 属于同一个已认证 WebRTC 对端，校验通过 DTLS 保护。接收仅对应当前视频源的 SSRC/负载类型，最多缓存 1024 个源包和 128 个校验组，200ms 到期；严格检查版本、包数、长度、帧尾、时间戳与恢复填充。切换视频格式、关闭对端会清理状态。重复或迟到的恢复数据继续由原有重排器去重，不绕过解码门控。

HUD 与 `native-probe` 报告分别显示校验包、校验内容字节、重建包与无效/丢弃数。重建计数也可能包含先于原始包到达的有效恢复，不能直接当作线路实际丢包数。校验协议概念参考 [RFC 5109 的 XOR 保护](https://www.rfc-editor.org/rfc/rfc5109.html)，传输使用 [RFC 8831 的 WebRTC 数据通道](https://www.rfc-editor.org/rfc/rfc8831.html)；具体封装是本项目独立实现的原生扩展。

验证包含每个单包缺失位置、序号回绕、乱序、重复、两包缺失、超时、错误源与预算；真实加密 UDP 夹具丢弃首个关键帧的一片，并持续丢弃该片的所有重传和 RTX，确认仍能恢复并解码后续参考帧。状态单测不代替真实跨网络效果验收。

HUD 主栏的 Loss 从原始 RTP 序号统计，宽限期后仍缺失的包不因 FEC / RTX 恢复而消失；修复后的剩余丢失另列。诊断保留 `loss_ppm` 的旧含义，新加 `network_loss` 记录原始交付的窗口分子分母、乱序、重复和超期包。它反映接收端观察到的交付，不能单独区分网络与接收端压力；详细定义见 [HUD](hud.md)。
