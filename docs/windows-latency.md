# Windows 视频延迟与计时范围

目标是在保留垂直同步的情况下减少客户端工作量。H.264、1080p、60 FPS 不足以单独决定解码耗时；解码接口、GPU 同步、显存读回、颜色转换和上传路径都影响结果。不能直接把不同客户端同名 HUD 数值当作同一阶段。

## 当前路径

0.8 及此前的图形观看路径：

```text
H.264 → D3D11 硬解 → 同步读回 NV12 → CPU 转 RGBA
      → ColorImage → RGBA 纹理上传 → UI 与视频绘制 → VSync
```

0.9的图形观看路径：

```text
H.264 → D3D11 硬解 → 同步读回 NV12 → 最新帧邮箱
      → Y/UV 平面上传 → GPU 颜色转换与缩放 → UI 绘制 → VSync
```

两者都保留硬件解码和默认垂直同步。平面路径去掉 CPU YUV 转换及逐像素 ColorImage 创建，1080p 每帧上传量从约 8.3 MB 降到约 3.1 MB。纹理存储按格式与尺寸复用。Windows 读回存储在最后一个 CPU 图像读者释放后归还到有界缓冲池，避免逐帧分配与清零；不外借映射指针。帧邮箱每个显示器仅保留最新图像，不增加显示帧队列；解码参考帧仍按序处理。

着色器支持 NV12、I420、BGRA，以及 BT.601/709 的完整和有限范围。初始化失败使用原 RGBA 回退。CLI 的 RGBA 消费接口保持兼容。

### Windows GPU 表面路径

支持 `WGL_NV_DX_interop2` 的驱动自动使用下列路径：

```text
H.264 → D3D11 硬解表面租约 → 最新帧邮箱
      → D3D11 视频处理器 NV12→RGB → WGL 共享纹理 → UI 绘制
```

此路径省去 NV12 同步读回和 OpenGL 像素上传，但仍有 GPU 颜色转换及 D3D/GL 同步，不能称为没有拷贝或等待。保留原有 VSync 设置和最新帧邮箱，不增加显示队列。租约持有 MFT 输出 sample，防止只保留纹理 COM 引用时解码池提前覆盖表面；MF 生命周期随最后一个租约结束。D3D immediate context 启用多线程保护。共享对象在 GL 锁定期间只读，转换在解锁后提交，输入 sample 保留到同步完成。GL 读取所有权保持到下一帧需要 D3D 写入时才归还，避免每次画完视频都立即阻塞等待归还，也避免纯 UI 重绘重复切换所有权。

驱动不提供扩展、设备不能共享或转换/同步失败时，后续帧回退 NV12 读回和平面上传。`UU_D3D11_READBACK=1` 可在启动时强制原路径用于同机对照；日志中的 `d3d11-wgl-gpu` 才表示实际使用了新渲染路径。不同显卡和跨适配器显示必须分别验证。

`d3d11_surface_probe` 读取带 AUD 的合成 H.264 文件，对比 CPU/GPU 输出，检查跨帧及解码器销毁后的 sample 租约。其 RGB 读回仅用于测试，计时明确区分 CPU 解码加读回、GPU 解码提交和 GPU 转换并等待完成、额外的测试读回。`video_dma_probe --isolated-window-station GENERATED_AUD.h264` 在 Windows 独立窗口站比较 GPU 共享与 CPU 上传的最终 GL 像素；不支持 GL 的非交互环境不能据此声称已通过桌面呈现验收。

不能通过关闭防重放、丢弃 H.264 参考帧或关闭 VSync 来代替管线优化。

## HUD

- Decode 是解码调用耗时。Windows 读回路径包括 MFT 处理、GPU 完成等待及读回；GPU 表面路径只计输出 sample 前的调用耗时，后续 GPU 完成与共享等待发生在渲染阶段。两条路径的 Decode 数值不能直接当作完整客户端延迟。
- Render 是 eframe 一轮 UI 准备和绘制提交的 CPU 墙钟时间，包括可能阻塞的驱动调用；交换缓冲区的显式 VSync 等待已排除。它不是 GPU 时间戳测量，也不是端到端显示延迟。
- FPS、带宽、解码均值及 Render 使用约 500ms 的采样窗口；HUD 以 500ms 快照显示并缓存排版。视频和输入继续按原有节奏处理，统计采样不延迟帧。
- 显示器、分辨率、DPI 或布局宽度改变时，HUD 立即重新排版。

客户端诊断中的 `render_frame_window` 按当前原生串流窗口汇总约 500ms 的已完成绘制，分别记录准备、初始清屏、界面更新、绘制提交、窗口命令和 Present 的平均 CPU 墙钟耗时，以及样本数、窗口跨度和最大 CPU 帧耗时。前五段合计仍沿用原 Render 的计时边界，Present 单列，不改变 HUD 数值。驱动同步阻塞可能出现在清屏或绘制调用中；这些分段不是 GPU 时间戳或屏幕扫描时间。窗口关闭后释放对应累积状态，隐藏协调窗口不混入其它串流窗口的结果。

关闭 VSync 后 Render 仍可能下降，因为驱动排队与纹理资源的同步等待也会影响绘制提交。应分别检查上传和同步，不能据此认为必须关闭 VSync。

## 隔离验证

`video_renderer_probe` 仅绘制生成的像素并读取自己的 GL 帧缓冲。Linux 必须通过 `tools/native/input_smoke.py` 启动私有认证 Xvfb；Windows 必须显式指定 `--isolated-window-station`，创建全新的非交互窗口站。它不读取工作桌面、不发送全局输入或访问剪贴板。

默认测试颜色、方向、行填充、透明字节处理、格式/尺寸变化及复用；`--benchmark` 测试 1080p NV12 上传，`--rgba-reference` 使用原 RGBA 路径作为对照。结果中的 `pixel_pipeline_cpu_ms` 包括测试程序的像素准备和绘制提交；`ui_and_submit_ms` 扣除单独计时的 CPU 颜色转换。测试窗口缩放显示，因此这些数字不是全屏扫描或用户实际串流 HUD 的替代。

`UU_DECODE_PROFILE=1` 启用 Windows 解码元数据计时，按 120 次调用输出整体、同步读回、CPU 拷贝和剩余 MFT 工作。它不会保存图像；默认关闭。首次初始化应与后续稳定窗口分开比较。

## 候选的重复对照

在 Intel Arc B390 上，使用完全相同的 600 帧 1080p60 H.264 合成文件，按“复用缓冲 → 未复用缓冲 → 复用缓冲”运行，每个阶段创建 3 个解码器，各解码 600 帧，均无错误。两者都设置相同的 ICodecAPI 提示。这是尽快处理文件的独立解码测试，并未播放到 GUI 或改变 VSync。

对照源码为 `304a0ca58bf298e496282ad0284ddefca8044f63` 与 `2b1cc08d85336c839b4efb17a1e7af959b792e0b`。可在安装了 FFmpeg 的环境生成相同类型的输入；测试文件仅含生成的图案：

```sh
ffmpeg -f lavfi -i testsrc2=size=1920x1080:rate=60 -frames:v 600 -an -c:v libx264 -threads 2 -preset ultrafast -tune zerolatency -pix_fmt yuv420p -profile:v high -b:v 18M -g 120 -f h264 synthetic-1080p60.h264
```

Windows 解码检查只读取这个文件，不连接设备或播放声音：

```powershell
$env:UU_DECODE_PROFILE = '1'
.\uu.exe probe --h264 .\synthetic-1080p60.h264
Remove-Item Env:UU_DECODE_PROFILE
```

| 测量 | 未复用缓冲 | 复用缓冲，两次阶段 |
|---|---|---|
| 整轮平均，包含首次延迟初始化 | 3.28ms | 2.19 / 2.17ms |
| 排除每轮首个窗口后的 submit 均值 | 2.81ms | 1.86 / 1.85ms |
| CPU 存储、裁剪拷贝与 Unmap | 1.10ms | 0.21 / 0.22ms |

稳定窗口仍有约 1.35–1.42ms 的同步读回。MFT 其余 CPU 提交约 0.28–0.29ms，**它不等于完整 GPU 解码耗时**；部分 GPU 完成等待计入了读回阶段。首次冷启动结果不能直接当作稳定路径收益。

独立 Linux GL 像素上传对照中，1080p 输入缩放到 192×192 测试窗口，RGBA 的 UI/提交约 7.1ms，平面约 0.49ms；这不是 Windows 全屏或实际串流 HUD 的验证。Windows 非交互窗口站未提供所需 GL 窗口配置，因此保留该渲染实测限制，不据此桥接交互桌面。

## 与 Moonlight 及编码格式比较

Moonlight 的 Decode 和 Render 也有各自的计时边界；其 HUD 的 Encode 来自服务端处理延迟统计，不能仅凭标签判定是纯硬件编码耗时。对照应固定主机、内容、分辨率、帧率、码率、位深、HDR 和显示设置，并观察输入到画面的响应，不能将 H.264 SDR 与 AV1 HDR 的两张截图当作编码器独立对照。

UU 协议及已有兼容实现包含 H.265/HEVC，UU 并非只能使用 H.264。本项目 Windows UU 串流现可在“设置 → 视频编码”选择优先 H.265 / HEVC，切换时自动重连；默认仍为 H.264。尚未验证 UU 官方链路可协商 AV1，Moonlight 能使用 AV1 不代表 UU 协议也能。

## 4K GPU 路径原生对照

Intel Arc B390，3840×2160、60 FPS、120 帧合成 H.264，两个独立硬解器交替处理同一输入，排除前 10 帧。CPU 路径与 GPU 路径使用同一提交的解码器；测试未连接远端、采集桌面或发送输入。

首轮通过颜色校验后的结果：CPU 解码加 NV12 读回 **7.17ms**；GPU 解码提交 **0.50ms**，NV12→RGB 转换并等待 GPU 完成 **1.18ms**，后两者合计 **1.67ms**。测试额外读取 RGB 用于逐像素对照的 17.40ms 单列，实际共享渲染不执行这一步。这里没有测 WGL 互操作、窗口合成或屏幕扫描，不能宣称端到端延迟为 1.67ms。

随后两次同条件重复对照：CPU 路径 7.14 / 7.34ms；GPU 提交加转换完成 1.67 / 1.66ms，颜色误差相同，三轮均通过。

120 帧的 119 次跨帧租约检查及解码器销毁后表面读取通过；另一组 96 帧覆盖完整/有限范围、BT.601/709、960×540↔1920×1080 及编码高度裁剪，92 次同尺寸租约检查通过。RGB 平均绝对误差分别为 1.05、1.25（8 位通道单位）；硬件色度滤波与 CPU 参考在饱和边缘不逐像素相同。Windows GL 对照相应检查均差及大差异像素比例，Linux 同着色器路径仍执行原有最大误差门禁。

Windows 独立窗口站未提供所需 GL 配置，WGL 最终呈现实测仍需交互环境确认；不能把离线 D3D 校验当作实际串流验收。初始候选曾因颜色范围枚举写反而失败，修正为 SDK 命名常量后才通过；失败候选未安装到正式客户端。

- [Microsoft：VideoProcessorBlt 与 GPU 查询边界](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11videocontext-videoprocessorblt)
- [Khronos：WGL D3D11 互操作与锁定同步](https://registry.khronos.org/OpenGL/extensions/NV/WGL_NV_DX_interop2.txt)

首个部署版本的实际 4K 会话日志确认 `d3d11-wgl-gpu` 已启用，Decode 约 0.52ms、Render 约 3.65ms、解码错误为 0；旧会话分别为 7.6–8.0ms 和 0.60–0.69ms。后续延后归还 GL 所有权的优化另增 `video_gpu_submit_acquire_release_ms`，依次记录 GPU 转换提交、WGL 获取、WGL 归还的会话平均耗时，用于定位同步等待。实际画面与鼠标跟手程度仍须交互确认。

第二轮延后归还纹理后，实际 4K 会话 Decode 约 0.46–0.59ms、Render 约 1.26–1.92ms，用户确认拖动体验再次改善。新截图仍存在接收/解码 60 FPS、呈现约 53 FPS，不能把解码提速等同于端到端优化完成。官方对照截图未显示编码格式，不能据此把帧率差异归因于 H.264 或 HEVC。

后续曾尝试优先使用普通 D3D11 DEFAULT 纹理注册 WGL，但实际窗口出现同步耗时回退，现恢复优先显式 DXGI 共享纹理；驱动拒绝注册时才尝试普通 DEFAULT 纹理。`video_dxgi_shared_export` 记录最终选择。该选择符合 WGL 互操作的资源要求，性能收益仍需实际窗口验证。

启用 VSync 且最近 250ms 内选中视频流有新图像时，UI 连续请求重绘，让交换缓冲区控制刷新节奏，减少到帧唤醒与正在进行的绘制错相。停止收帧、最小化或关闭 VSync 后恢复事件驱动。重复重绘不增加 Render FPS；统计仍只计算消费了新图像的绘制提交，不表示屏幕扫描完成。`presentation_vsync` 记录启动时真正使用的设置；`video_mailbox_published_replaced_delivered` 为选中轨道累计发布、被更新图像覆盖、交付 UI 的数量，用差分判断 UI 未及时消费的丢帧。这与压缩帧队列溢出的 `queue_drops` 不同，替换过时图像不破坏解码参考帧，也不引入显示排队。

第三轮实际截图接收/解码 60 FPS、呈现约 55.4 FPS，Decode 0.59ms、Render 4.16ms；用户感觉停顿减少，但 Render 回退至 4–5ms。日志确认普通资源路径生效，WGL 获取锁会话平均约 5.3–5.7ms，明显高于第二轮约 0.4–0.6ms。邮箱覆盖约 2%，解码错误和压缩队列溢出为 0。由于该轮同时改变纹理资源和刷新节奏，不能据此单独确认因果；下一轮只恢复优先显式共享资源，保留刷新调度以隔离变量。离线 D3D 颜色/租约通过不能证明 WGL 同步性能无回退，恢复后的实窗收益仍待确认。

恢复显式共享纹理后，实窗仍出现 Render 4.6–5.0ms，WGL 获取约 3.3ms、归还约 4.2ms。仅改变资源选择不足以消除回退，现撤除第三轮增加的连续刷新，恢复由新图像和输入事件唤醒 UI。恢复后的实际延迟仍需重新验证。

### HUD 延迟合计的范围

原 Network 标签改为“控制 RTT”：它测量 CONTROL 应用消息往返，包含协议处理、排队和对端响应，均值后的 ± 是最近 32 次样本的标准差。ICMP ping 测量范围不同，局域网 ping 1ms 与控制 RTT 5ms 并不矛盾；不能把后者归因为纯网络线路慢，也不能直接用 ping 替换。

“已知段合计”近似相加控制 RTT、Decode、解码后邮箱等待和 Render。邮箱等待按选中轨道最近 2 秒、最多 120 个实际交付图像统计，覆盖旧图像时重置发布时间，不把被淘汰图像混入；没有新样本显示未知。计时仅覆盖发布到 UI 取走，未覆盖后续交换缓冲和屏幕显示。控制 RTT 过期时合计也显示未知。

这个合计不是同一输入对应帧的全程测量，也不是严格下界。输入事件等待、远端捕获/编码、视频组帧/解码前队列、VSync/合成/扫描等仍未完整测得，因此 HUD 同时明确显示“总延迟待测（远端/呈现未计）”。不使用任意固定编码耗时或帧周期补出一个看似精确的总数。真实端到端比较仍需要输入触发标记与画面响应测量。

### 60/120 FPS 波动与接收统计反压

后续实机对照：60 档截图 Rx/De 47.7、Rd 45.6、Decode 0.50ms、Render 2.06ms；120 档 Rx 119.5、De 121.5、Rd 113.6，说明客户端不存在统一的约 50 FPS 吞吐上限。120 档同时有更多重传/坏帧，不能把提高帧率当作解决传输抖动。Rx/De/Rd 是各自约 500ms 窗口的速率，窗口边界和少量积压会造成瞬时 De 高于 Rx，不能按单张截图相减推算丢帧率。60 档当前不足已出现在接收阶段，仍需区分源端输出节奏、网络与本机接收堆积；不预先归因为编码格式或单一渲染瓶颈。

发现并修正一处确定的接收阻塞机制：[webrtc-rs 0.11 TWCC 接收路径](https://github.com/webrtc-rs/webrtc/blob/v0.11.0/interceptor/src/twcc/receiver/receiver_stream.rs)逐个 RTP 包等待容量为 1 的元数据通道，同一个统计任务还负责等待 RTCP 写入。反馈发送停顿会反压视频读取，并把本机等待混入后续到达时间。现在协商不变、继续复用原 RTCP 编码器，接收时只记录有界小型元数据，独立任务发送反馈；任何网络写入都不持有接收锁。元数据上限 16384，极端反馈阻塞时淘汰旧元数据并统计 `twcc_metadata_drops`，不阻塞或丢弃视频数据。测试先复现原路径在反馈停顿时无法交付后续包，再验证新路径继续交付 128 个原样包、反馈包序号/数量正确、无扩展直通及关闭可取消；这不是实际串流已稳定60的证明。

新增 `frame_cadence`：按约 500ms 窗口记录源 RTP 时间戳间隔、客户端新时间戳到达间隔、解码队列等待，分别为均值/P95/最大值（毫秒）。重复/迟到/RTX 时间戳不算新帧，支持32位回绕。它不依赖双方时钟同步，也不测视频单程传输延迟。源时间戳间隔约20ms且到达相近，表示收到的源图像节奏约50 FPS；源间隔约16.7ms而到达长短成团，表示传输或接收调度引入突发。源端主动跳帧与整帧丢失仍需结合丢包/恢复计数区分。`receiver_tick_late_ms` 另外记录本机接收轮询定时器超过计划唤醒点的时间，帮助区分本机定时/调度延迟，不能当作网络延迟。另计 `decoded_display_skips_all_tracks`，区分解码后为追赶最新帧而省略的交付与邮箱覆盖，不改新帧 FPS 的口径。

控制 RTT 仍显示均值±标准差，另显示同一最近32次样本的 P95，悬停可查看最新/最小/中位/P95/最大。P95表示约95%样本不超过该值，±不是上下界或测量误差。标准差可能大于均值，例如31次1ms加1次100ms：均值约4.1ms、标准差约17.2ms，而中位数仍1ms。每次探测记录分布与本地发送调用耗时，回包计时终点取消息处理入口，排除随后本地解析工作。不能仅凭这些数据把高RTT归因于物理网络；发送调用结束也不等于数据已到远端。

官方 Windows 客户端和被控端的本地协议描述符再次核对：60为枚举2且fpsCount60，120使用fpsCount120，当前请求未见档位编码错误。该证据只验证字段，不揭示官方闭源的采集/节流调度；现阶段不通过修改60请求为120或重复画面来伪造满帧。

### Windows 接收定时精度

持续播放高频动画和60帧视频的后续会话中，60档仍出现源时间戳平均约19–21ms、P95约33–34ms，而解码前排队通常只有0.01–0.04ms。动态内容的存在排除了“截图时鼠标没动，所以桌面没更新”的解释；当前瓶颈已出现在所收到的源帧节奏中。TWCC统计已生效且无元数据溢出，说明解除统计反压并未单独解决60档不足。RTP时间戳仍不能区分官方采集、编码、发送适配的具体耗时。

同时发现Windows短定时器精度不足。使用与客户端相同版本、启用网络I/O的Tokio，在同一进程依次执行默认、申请1ms、恢复默认三个阶段，各等待400次5ms定时器。首轮默认平均晚醒12.60ms、P95为15.24ms；申请后分别为1.39ms、2.03ms；释放后回到12.97ms、15.30ms。默认阶段400次约耗时6.1秒，申请后约2.0秒。独立的线程sleep对照没有出现相同幅度的差异，因此不能拿线程sleep的精度代替异步I/O定时器的验证。

两种连接共用的视频接收路径现在按有效视频轨道持有1ms定时精度请求，普通结束、错误和异步取消均通过RAII释放。Windows对多次请求配对计数，多轨道退出互不提前释放；主页和非串流进程不持有该请求。诊断事件`video_timer_resolution`记录请求值及API返回码，返回成功也不等于所有唤醒都能精确到1ms。没有修改目标帧率、丢帧策略、时钟计时或渲染调度。

随后直接使用生产RAII实现重复对照：平均晚醒13.21ms→1.21ms→13.03ms，P95为15.47ms→1.95ms→15.43ms；第三阶段取消持有请求的异步任务后恢复，验证了取消路径释放。两轮均未运行GUI或测量真实输入到画面的响应。

这遵循[Microsoft定时精度API的生命周期要求](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod)，并参考[Moonlight串流期间申请、结束释放定时精度的做法](https://github.com/moonlight-stream/moonlight-qt/blob/master/app/streaming/session.cpp)，实现独立编写。精度请求会增加唤醒频率；Windows11对完全遮挡、最小化等进程仍可能限制其效果。这项优化针对本机定时等待，未证明官方源端60档已稳定或端到端延迟下降相同数值。

可在Windows运行`cargo run -p uu-core --release --example timer_resolution_probe`复测生产代码使用的计时资源，第三阶段通过取消持有资源的异步任务验证释放。测试只产生定时事件，不连接设备、捕获桌面或注入输入；性能数值应在目标机器测量，不作为跨机器固定阈值。

### 高码率下的拥塞反馈时间失真

复核后续日志时必须把实际宽高与帧率一起比较：自动画质会话曾在请求4K不变时，收到1440p和1080p图像。接近60 FPS的连续片段实际为1080p，不能作为4K改善证据；实际4K片段仍约47–60 FPS。低码率更稳定的用户反馈促使排查逐包拥塞反馈，而非继续压缩已很短的解码时间。`video_stats`现在同时记录实际`width`、`height`和`bitrate_kbps`，用于分段比较。

确认另一处独立错误：所用TWCC记录器保留未量化的到达时间，RTCP编码却将每个差值截断为250微秒单位，导致每个包都丢失余量。400包间隔120或240微秒时，序列化后重建的末包时间分别落后约47.9或95.8毫秒；反馈中会凭空出现压缩的到达节奏和跨报告的跳跃，包速率越高越明显。这类反馈失真可能干扰发送端带宽适配，但尚不能据此宣称真实4K帧率已修复。

现在在进入记录器前将绝对到达时间量化到最近的250微秒，确保差值可被精确编码，时间误差始终不超过125微秒且不随包数累积。这遵循TWCC的线格式；[Pion记录器](https://github.com/pion/interceptor/blob/master/pkg/twcc/twcc.go)采用保留量化余量的方式达到同样目的。本实现继续使用现有编码器，避免修改第三方依赖。回归检查实际序列化/反序列化后的时间线，覆盖不同包速率、连续报告、序号回绕、丢包和负时间差，并保留反馈写入阻塞时视频仍能继续接收的测试。

用户随后反馈该修复仍未稳定60帧，偶尔降至约35帧。新日志确认运行修复版、实际4K H.264且无坏帧/解码错误/队列溢出；实际35–43Mbps片段仍约48–58接收FPS，源时间戳P95约33–36ms。低帧率也出现在低码率片段，不能仅凭相关性认定带宽是唯一原因；局部反馈缺陷已修复，端到端卡顿尚未解决。

### Windows HEVC 可选路径

切换编码需要同时实现能力声明、SDP、RTP组帧和解码。选择HEVC后先用内置生成的128×128灰色视频检查实际硬解输出；成功才在UU DecoderCap、streamer JSON及SDP中加入优先HEVC和H.264后备。HEVC能力限制为Main 8-bit 4:2:0，尺寸上限4096×2304；没有扩展、硬件不兼容或强制软件解码时不声明HEVC。CONTROL中的编码请求以双方实际协商结果为准，H.264-only远端继续收到H.264请求。

RTP使用[RFC 7798](https://www.rfc-editor.org/rfc/rfc7798.html)的非交错单NAL、AP、FU组帧，与H.264共用有界乱序、NACK/RTX、丢包恢复和显示路径。同一SSRC切换编码时清空旧分片并开启新的参考帧代际，AU携带编码类型；迟到的旧格式包不能切回旧解码器。HEVC损坏数据不会交给OpenH264。SPS尺寸/色彩读取复用已有BSD许可的ChromiumOS解析器；[Windows HEVC MFT](https://learn.microsoft.com/en-us/windows/win32/medfound/h-265---hevc-video-decoder)输出继续使用现有NV12 GPU纹理租约、颜色转换和WGL呈现，未调整渲染调度。

目标GPU上的生成4K60 HEVC素材离线验证通过，GPU解码提交平均约0.50ms、转换及同步约1.02ms，旧纹理跨帧保留及解码器退出后的租约检查通过。这里的提交耗时不包含完整GPU完成时间，也不是端到端延迟；128×128启动探测不能证明所有高分辨率都达到目标帧率。官方远端是否实际选择HEVC，以HUD和`video_stats.codec`为准，真实流畅度仍需实流对照。

离线GPU验证工具支持`cargo run -p uu-media --release --example d3d11_surface_probe -- GENERATED_AUD.hevc hevc`；素材必须是自主生成、带AUD的Main 8-bit视频。Windows隔离回归`windows_generated_srtp_switches_h264_hevc_h264_on_one_track`使用本机加密连接和生成视频检查完整接收/解码路径，不打开窗口、不采集桌面、不发送输入。

该版本已通过Linux媒体72项、核心133项、GUI95项及Windows核心132项、媒体73项原生测试；Windows GUI默认回归与独立键盘消息泵测试进程均退出成功。AMD和Intel两块GPU上的真实HEVC启动探测与加密同轨道切换均通过：每台机器的H.264、HEVC、H.264三段各收到24个解码图像，各累计72帧、解码错误0。以上验证覆盖客户端实现，仍不替代官方被控端4K60实际帧率与交互验收。

### HEVC 首次实流与重连差异

用户首次选择HEVC后，HUD显示实际3840×2160、H265、目标60 FPS及物理屏120Hz，但接收和解码约30 FPS。日志确认60帧设置在编码切换前后各发送一次，远端均回复接受；同轨道从H.264切至HEVC后，源时间戳平均间隔仍约33.3ms。后续65秒累计解码约30 FPS，解码约0.49–0.65ms，没有新增压缩队列丢帧、坏帧或解码错误。启动时已有18次队列丢帧，不能表述为整个会话完全无丢帧。

用户随后退出重连，明确反馈60帧稳定。两次后续会话保持实际3840×2160 HEVC，源间隔约16.7ms，接收/解码接近60 FPS；其中约60秒的累计解码速率约60 FPS，坏帧、解码错误、压缩队列丢帧均为0。这确认官方远端与当前客户端组合可以实际运行HEVC 4K60。首次30帧不能解释为客户端漏发60帧设置；是否由首次编码器重配置或远端状态恢复导致，现有接收端日志不能确定，不据此增加周期重发或强制重连。

接收/解码达60仍需与呈现分开判断：后续日志的呈现采样多数约53–59 FPS，Render约5.8–10.1ms，仍有本地呈现等待。用户确认的稳定性改善不等于所有阶段或端到端延迟都已达到目标。

### 局域网鼠标跟手与 VSync 对照

另一台Intel UHD接收端在实际1080p60 HEVC串流中，控制RTT约1.8ms、Decode约0.77ms、Render约2.65ms，但解码后待绘制约7.4ms，接收/解码61.4 FPS而呈现53.7 FPS。此时HUD的已知段合计约12.6ms，仍遗漏输入事件等待、远端捕获/编码及最终呈现；不能按这个数字判断鼠标到画面的响应只有十几毫秒。

当前egui窗口在同一个线程处理输入、准备画面和交换缓冲。鼠标事件在界面更新时批量转发，VSync交换等待也会延后下一次输入处理与解码图像交付。Render采用eframe的CPU统计，明确排除了交换缓冲等待，因此低Render不能排除这一阶段的延迟。[WGL交换间隔规范](https://registry.khronos.org/OpenGL/extensions/EXT/WGL_EXT_swap_control.txt)定义间隔0为不等待视频刷新周期；桌面合成和屏幕扫描仍由系统执行，不能将关闭VSync理解为所有呈现等待都消失。

同一版本关闭VSync、重开串流后，用户明确确认拖动跟手明显改善。日志确认实际仍为1920×1080 HEVC，`presentation_vsync=false`：约145秒、30个统计样本的待绘制中位数降至1.74ms，高码率动态样本中位数2.20ms；此前两个开启VSync的会话分别为5.28ms、6.99ms。累计解码图像的邮箱覆盖比例从约10.6%–11.5%降至6.4%。这些是不同会话的统计，不是严格相同内容下的基准：关闭后的主要动态片段实际码率约40–46Mbps，此前主要约26–43Mbps；新会话还有7次压缩队列丢帧、局部低呈现FPS，不能宣称全部卡顿或端到端延迟已解决。

对于优先跟手的Windows串流，可在画质菜单即时取消“垂直同步”，或在串流设置中保存后立即应用，保持相同分辨率、帧率及光标模式比较；检查日志的`presentation_vsync`确认实际生效。关闭可能出现撕裂，若需要更平滑的画面可恢复。鼠标拖动仍需观察远端窗口内容，单纯改为本地光标只能改变光标自身的显示方式。

后续若在关闭VSync后仍有明显差距，应测量输入事件到发送的等待与实际显示延迟，并考虑把输入处理和可能阻塞的呈现分离。Moonlight的渲染线程和非阻塞DXGI呈现可作为设计参考；不直接把其交换链参数套到当前WGL路径，也不重新修改已通过实机验收的键盘归属。
