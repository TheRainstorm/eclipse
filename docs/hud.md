# 串流 HUD

串流菜单的“更多 → 启用 HUD”直接切换统计显示，HUD 只保留 Compact 精简模式；旧详细模式设置读取后自动使用精简布局，开关和外观配置继续保留。“设置 → 串流界面”可调整 HUD 垂直位置、主栏及诊断卡背景不透明度，三项范围均为 0–1。位置 0 靠顶、1 靠底，始终将完整 HUD 限制在画面内；背景 0 为透明、1 为不透明，文字不随背景淡化。默认位置为 1/30，主栏不透明度 0.75、诊断卡 0.80；旧配置自动使用默认值，可一键恢复。参数随客户端配置保存，应用后生效。默认 Ctrl+Alt+Shift+S 切换显示（可在应用设置修改），悬停可展开诊断详情。主 HUD 保留 FPS、RTT 等通用缩写；悬停详情与应用语言同步。

Compact 使用带圆角、不透明度约 75% 的半透明深色底，默认距画面顶部约 3.33%（1080 高度时约 36 点），为顶部内容留出空间。依次显示实际分辨率@目标 FPS 与编码色彩、`FPS · Rcv/Dec/Rnd`、蓝色的 `BW 链路吞吐 · RTT ± · Loss`、`Latency · Cap+Enc/Dec+Rnd · Est. ≈均值 ±标准差` 和 `E2E · Video … · Input→Frame …`。窗口较窄时按完整字段组换行。HDR 仅在实际协商 HDR10 时标注。

Windows 原生 D3D 呈现路径在双方协商端到端扩展后，默认查询 DXGI PresentCount 回执，并按同帧身份和跨机校时生成“DXGI回执估测”。显示区间从该图像最早已知提交前到首次读到对应回执后；它不以 Present 返回、GPU 完成或刷新率推算显示时刻。**这是有平台统计假设的经验区间，多显示器或其它全屏应用可能使 DXGI 统计不可靠，不能宣称为平台保证的硬误差界。** 缺少帧身份、源时间、有效校时或回执时保持未知，主机未协商扩展时显示“不支持”；纯 WGL 等尚无回执的路径不会回退阶段和。生成预览只检查布局，不是实测结果。

悬停诊断显示解码后端、采集时间、处理 / 网络 / 排队拆分与源刷新率。Est.Total 将采集、编码、解码、UI 提交、RTT/2 和三项队列的完整分量和每 500 ms 采样一次，显示最近 3 秒采样的均值 ± 标准差。± 只表示这些估计值的波动，与 E2E 的区间误差含义不同；不足两个样本时显示 `±—`，任一分量缺失时显示未知，并断开曲线和滚动统计。悬停详情按画面、帧率、编解码、网络、延迟、端到端、统计、恢复统计、异常统计、输入响应、收包、恢复原因分类，与应用语言同步；分类和数据首行对齐，每类按颜色区分。

| 字段 | 统计含义 |
|---|---|
| FPS recv/dec/rnd | 最近窗口的接收、解码、当前视图绘制帧率；rnd 不等于显示器扫描输出帧率 |
| BW | 实际选中直连路径所在本机网卡 RX+TX 的吞吐，包含其它应用流量；视频码率在“画面”行单独显示 |
| RTT ± | 控制消息往返时间均值 ± 标准差，最近 32 个样本；不是 ICMP Ping |
| Loss | 最近约 500 ms 窗口内，原始 RTP 在乱序宽限期后仍未到达的包数 / 期望包数；FEC 与 RTX 修复不抵消这个值 |
| After repair | 详情中保留的接收器超时未恢复丢包率；原有诊断字段 `loss_ppm` 保持此含义 |
| enc/dec/rnd | 编码、解码调用、UI 准备及渲染提交的窗口均值，单位 ms；GPU 等待可能在提交阶段发生 |
| 端到端 / E2E | 同一源画面从主机源呈现到客户端系统显示的估测；帧身份、时钟映射和回执完整时报告 `≈均值 ±误差 ms` 并标出显示方法，缺失时未知 |
| 均值误差与方法 | 对同一批区间分别取上下界均值，主项 `±` 向外覆盖该均值区间及微秒舍入；不要求样本独立，不消除共同校时偏移。DXGI 方法仍依赖统计可信假设，不是多屏平台硬界或 RTT 标准差 |
| 单帧最大半宽 | 当前样本中最大的单帧区间误差，独立于主均值误差；P50/P95 仍为单帧区间中点的分位数 |
| 源/显/观测丢弃 | 来源、显示回执及真实观测丢弃累计数；观测丢弃包括钩子或队列丢失、非法元数据，不含历史容量淘汰，也不是媒体丢帧数 |
| 历史淘汰 | 四种有界历史表达到容量时移除的条目数；一帧可占多个表，不表示当前观测或媒体丢失 |
| Est.Total（估计） | 最近 3 秒完整分量和采样的均值 ± 标准差；分量包含 cap + enc + dec + rnd + RTT/2 + 主机发送等待 + 解码队列 + 邮箱等待，不是同帧端到端测量 |
| Est.Total 缺项 | 任一分量未知则总值留空；恢复后重新累计连续有效采样，不补零、不跨缺口或代次统计 |
| 输入响应 / Input response | 显示实际输入的排队+上行、输入至注入、后继源等待和 Input→Frame；对应应用的视觉响应仍需因果证据 |
| 注入确认 / Injection ack | 抽样输入发出，经主机系统接受注入，再收到确认的往返时间；不证明应用已响应或对应画面已显示 |
| 长间隔 | 前台可见串流的新画面提交间隔超过 max(3/预期帧率, 20 ms) 的次数；持续等待只计一次，详情按所选 3/10/60 分钟窗口保留，1 秒时间桶边界精度；现有自动诊断仍使用精确的 60 秒窗口 |
| Max gap | 同一窗口内最长的新画面提交间隔，包含进行中的长间隔；不代表显示器实际扫描间隔 |
| 源至发完 | 主机同一 QPC 时钟中，新源画面呈现到最后一个 RTP 写入 API 返回的均值/P95；包含采集前画面年龄及编码、排队与发送，和已知分量和中的阶段重叠，不能再相加 |
| RTP 跨度 | 同一帧首个到最后一个 RTP 写入 API 返回的均值/P95；区别于生产线程等待发送队列，不代表网卡发完 |

Loss 用于观察修复之前的缺包波动。乱序宽限期默认 60 ms，与接收器一致；原始包在宽限期内补到不记丢失，重复包不增加分母，超期原始包单独累计为 late。序号回绕会展开；无法解释的跳变使该窗口显示未知。静止、断流或没有可统计的包时也不伪造零丢包。诊断中的 `network_loss` 记录窗口分子分母和原始包累计数。

这里观测的是应用接收端看到的交付结果，可能来自网络链路、接收缓冲或调度压力，不能只凭 Loss 定位物理链路。结合 RTT 波动、接收 FPS、FEC/RTX 恢复数和修复后损失判断；FEC 恢复成功而 Loss 大于零是正常的。

可用的视频端到端测量要求按同一帧的源身份、编码输出 PTS 和实际 RTP 身份关联两端。跨机 QPC 或单调时间戳不能直接相减：四时间戳交换利用路径延迟非负约束偏移上下界，不假设往返对称，再按相对时钟漂移上限扩大区间。详情暴露当前漂移假设；当前为 1000 ppm 的工程上限，不是操作系统保证的精度。源时间或校时样本超过五秒后不再映射，端到端窗口只保留最近三秒实际显示的有效样本，晚到遥测不会让旧显示重新变新。

可用时，主均值和误差来自同一批同帧延迟区间的上下界均值；P50/P95 保持为各帧区间中点的分位数，主均值的误差不适用于这两个分位数，最大单帧区间误差另列。它们必须结合显示方法解读，中点不是精确时间。即使有系统显示回执，也没有测量物理面板扫描后的像素响应，更不能把它等同于鼠标到屏幕响应。完整物理延迟仍需外部测量。详见[原生延迟统计](native-latency.md)。

DXGI Count 跳跃只接受明确报告的 ID，不认定被跳过的图像没显示；重复回执不增加样本。统计全零、非 S_OK、DISJOINT、计数倒退或回绕、元数据缺失及窗口/surface/媒体/观测换代会退役旧关联，缓存旧图像不会借新提交伪造首次显示。不要求刷新计数非零，也不调用 DwmFlush 或新增 GPU 等待。原始 Present profiling 开关仍独立控制后台文件，和默认估测共用同一次查询。

Est.Total 使用已列出视频阶段的独立窗口均值，各阶段不是同一帧的完整关联测量。它没有测量输入设备与输入去程、远程应用响应、等待下次采集、未覆盖的组帧等待、GPU 完成、呈现队列、合成、扫描及像素响应。RTT/2 仅假设往返链路对称，不能据此断言鼠标到屏幕只有几毫秒。

历史曲线随顶部 3/10/60 min 切换，显示视频端到端与 Est.Total（图例名“估计”）。端到端使用白色实线及误差竖线，估计使用淡黄色虚线及采样标准差竖线；其余项目仍是独立阶段窗口均值，网络项目明确为 RTT/2。图例标签使用无边框按钮并保留文字内边距，始终单行，极窄窗口可横向滚动标签；点击分别开关曲线。未知端到端样本留空，不用阶段和或零补齐。连接、媒体、轨道或显示观测代次改变时重新记录，显示方法改变也不连接旧数据；采样间隔超过一秒时也断开曲线。

原生主机支持逐帧遥测时，详情另列上述两个同钟跨度。每个跨度都按自身有效样本计算，不把不同总体的均值相减来填补缺失阶段。遥测超过五秒未更新或来自已退役媒体 epoch 时显示未知；没有源时间戳时，“源至发完”保持未知。它们不能与视频小计再次相加。

长间隔以提交给渲染器的新画面为边界，相同图像的 UI 重绘不计新帧。预期帧率取目标 FPS 和已知源刷新率较小者；165 FPS 时阈值为 20 ms，60 FPS 时为 50 ms。失焦、最小化、切屏、切换设备及帧率改变会重置比较基线，恢复后至少收到两帧才报告数值；媒体换代清空该轨道统计。详情显示阈值、当前连续观测时长及进行中的等待。观测不足一分钟时仍显示实际次数，不外推为每分钟发生率。

v0.20.3 起，暂停观测会保留此前已显示的持续停图记录及最近一次前台观测到的等待长度，直到这条记录超出 60 秒窗口。后台停留时间不会继续累加，恢复后不会把同一次停图再计一遍；未在前台观察到的暂停间隔不转成停图记录。每个间隔按发生时的预期帧率判定，详情中的阈值是当前值。

源空闲、采集节拍、传输丢帧、解码或 UI 调度都可能产生长间隔；计数不会直接把原因归到网络，也不能检测内容内部的动画卡顿或物理屏幕扫描异常。诊断元数据的 `video_continuity` 保存同一统计口径。

悬停面板背景不透明度约 80%，以当前串流客户区为边界，最大宽 1120、最大高 520 个逻辑点；窄窗口使用单列滚动，宽窗口将详情与曲线并排，左右按 6:4 分配内容宽度，为单行图例留出空间。分类和数据使用相同的首行顶端布局，可拖选字段并按 Ctrl+C。“延迟”分两组：首行是 Est.Total 均值及波动和处理、网络、排队合计；第二行是发送、解码、邮箱等待及源至发完、RTP 跨度，窄窗口继续换行。编解码行将采集+编码、解码+呈现提交两两分组；呈现提交仍为 CPU 耗时，不含系统显示等待。顶部提供“复制诊断”和“固定”：复制当前指标及所选统计窗口的纯文本，不包含连接地址、凭据或画面。未固定时，鼠标在 HUD 和诊断卡之间移动保持显示，完全离开后经过短暂宽限一次收起；诊断卡不使用逐次淡入动画。固定后移出鼠标或窗口失焦仍保持显示；固定本身不占用键盘。点击详情后的文字选择归本机，点击画面、Escape 或失焦释放键盘占用；Escape 同时解除固定。曲线浮框统一使用半透明黑底，白色端到端曲线数值保持可读。

延迟行中的网 / net 为 RTT/2 估计，排 / que 为发送等待、解码队列、画面邮箱三项之和。网络行保留 RTT，不再重复展示单程字段。源刷新率来自主机枚举的显示器模式，未知或旧主机的零值显示为缺省，而不是 0 Hz。


详情顶部的 3/10/60 min 选择器控制恢复、异常、原始收包和长间隔统计。计数器使用实际保留的差值，最多保留 60 分钟、约 500 ms 一次采样；窗口尚未填满时显示“已记录”的实际时间，不换算为满窗口次数。连接、媒体、轨道或计数器重置后重新记录。长间隔只观察前台可见提交，后台停留不产生虚假卡顿。视频端到端仍使用最近三秒的有效同帧样本，曲线展示所选的最近 3/10/60 分钟，横轴和纵轴按可见数据更新；切换查看范围不改变这些点的测量口径。最多保留 60 分钟、每 500ms 一点，换代清空。长时间范围按横向像素保留端点、数值和误差极值，缺失与时间缺口保持断线；浮框始终查询原始采样。

“链路吞吐”是实际选中直连路径所在本机网卡 RX+TX 的字节差分，RX/TX 另列；包含该网卡其它应用流量，区别于视频码率、网卡标称速率与可用带宽。“ICMP Ping”向选中直连端点每秒发送一个 echo，超时 200 ms；Windows 使用系统 ICMP API（毫秒精度，零值显示 `<1 ms`），Linux 使用普通用户 datagram ICMP socket，不请求额外权限。防火墙、权限、缺少适配器、路径变化、带 scope 的 IPv6 链路本地地址或中继路径不能可靠测量时显示 `—`。HUD 隐藏后停止请求采样，已有结果三秒过期。探针在连接监控的后台阻塞工作中运行，媒体收包和 UI 不等待它。实现依据：[Windows ICMP](https://learn.microsoft.com/en-us/windows/win32/api/icmpapi/nf-icmpapi-icmpsendecho2ex)、[接口计数器](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-getifentry2)。

帧率没有以 `1000/FPS` 的固定罚时加到 E2E 中。详情另列串流帧周期（目标 FPS）和源帧周期（源刷新率），只作节拍参考：60 fps 为 16.67 ms，30 fps 为 33.33 ms。真实采集等待取决于相位与可用源画面，不能一律减掉半个帧周期。当前 DXGI 回执区间的上界取首次查到对应回执的时间；如果查询随绘制节拍变慢，区间可能变宽、估测中点可能升高，不等于真实延迟同幅增加。因此详情同时显示均值区间和误差，结合源至发完、编解码、队列及同帧 profiling 判断。不同总体的阶段均值不能用 E2E 减去小计来填补未测显示等待。

## 输入路径与后继画面

保持 HUD 的字段顺序、颜色、锚点与外观设置。`Cap+Enc` 是采集和编码的阶段和，`Dec+Rnd` 是解码和 UI 呈现提交的阶段和；系统显示等待由回执口径单独处理，不将 CPU 提交耗时冒充完整呈现。

`Video` 保留源画面到系统显示回执的同帧估测。`Input→Frame` 使用同一次实际输入的客户端入队时刻、主机注入完成时刻，以及注入后已观测源图像的首显证据。它包含输入送达、后继源画面等待和视频路径，**并不证明游戏或其它应用已经响应了该输入**：桌面其它动画也可能产生源更新，未观察到的更早源画面也无法凭空恢复。任意应用的输入到目标像素响应仍需应用标记或其它因果测量，诊断中的“视觉响应”据此保持未知；不会将输入确认 RTT 与独立视频均值相加。

输入最多每 250 ms 抽样一次，使用最近 3 秒收到有效注入回执的样本。诊断另外显示：

- **排队+上行**：同一次输入从客户端入队到主机 CONTROL 回调收到，复用四时间戳校时的保守区间，不假设单向路径对称。
- **输入至注入**：入队到主机系统注入成功，已经包含前一项、主机排队与注入，不能再重复相加。
- **后继源等待**：主机同一时钟下，注入成功至匹配后继源图像更新的等待。它不能单独识别游戏更新和渲染成本。
- **输入样本/画面匹配**：有效实际输入抽样数和具有源身份、首显证据的匹配数，说明观察覆盖。

送达与注入的 `±` 表示同批均值的校时区间，不是样本波动；送达 P95/σ 另报区间中点的分位数和标准差。Input→Frame 的 `±` 保留显示回执估测的误差及方法，不成为物理输入到光子的硬保证。旧主机没有新增能力公告时继续使用旧输入协议，新增字段保持未知；空闲、换代、失去显示证据或样本过期后不沿用旧值。

粉色“输入→画面”曲线和白色视频曲线分别保留自己的误差；未知处断线。它与估计阶段和独立，也跟随 3/10/60 分钟查看范围。

生成数据的显示示例：

```text
Latency · Cap+Enc/Dec+Rnd 6.9/3.5 ms · Est. ≈12.78 ±0.12 ms
E2E · Video ≈26.91 ±5.26 ms · Input→Frame ≈34.40 ±6.20 ms
```

这些数字只说明显示格式，不是性能测量，也不能将两项均值相减推算精确游戏延迟。
