# 构建、验证与发布

工作流位于 [build-release.yml](../.github/workflows/build-release.yml)。正式发布需要 Linux、Windows 的完整验证及包内文件校验全部通过。

## 执行顺序

1. **Source and release preflight** 先解析源码提交、检查标签格式、版本与发行说明，再统一执行源码和发行工具测试。
2. **Build Linux / Windows** 构建目标提交并运行平台测试；Linux 同时验证隔离桌面、采集、输入、音频和托盘生命周期。媒体快速验证及 Windows 安装器验证独立运行。
3. **Windows executable smoke test** 在 Windows runner 实际加载完整包，验证加密音视频、输入、配置和剪贴板等。
4. **Publish tagged release** 核对标签对应的提交与两端压缩包，生成以版本命名的附件及 `SHA256SUMS`，然后发布。

主分支提交与 PR 运行完整构建。如果一次原子推送同时更新主分支和指向同一提交的正式标签，主分支执行源码检查，完整双平台验证由该标签工作流负责。手动验证仍执行完整构建。标签与手动重建同一标签共用并发组，已有正式资产保持不变。

## 手动验证已有标签

在 Actions 页面选择工作流，填写已推送的完整标签，例如 `v0.24.5`。解析阶段会获取并验证目标标签；缺少 `v`、标签不存在、版本不匹配或没有发行说明时，会直接提示错误。

产品始终从解析出的固定提交构建。单独的验证任务可以使用当前工作流的修复夹具；这不会改变平台构建任务的产品源码。取消勾选 `publish_release` 可仅验证已有标签。

## 定位失败

先查看失败的 job 和步骤，再查看错误前后的日志。编译、单元测试、桌面集成、安装器和发布各自保留检查结果。

Linux 桌面验证失败时，`diagnostics-linux-x86_64` 附件保留生成桌面的日志、截图、窗口几何与等待阶段。`wait-failure.json` 区分窗口映射、首帧、焦点、全屏和缩放等条件；其中的进程退出状态用于区分启动失败和状态等待。已经构建完成的包也会保留为 Actions artifacts，便于复现。

测试使用独立配置和自有桌面、音频端点，不连接开发者的真实设备。运行库、编译参数及 CMake 派生缓存会影响缓存可用性；构建工具应校验其来源，不把本机已有文件当成完整包已经生成的证明。

取消的运行、账户或 runner 调度失败与测试失败应分别统计。真实测试失败继续阻止发布；恢复发布时使用原标签和固定产品提交。
