# uu-remote 产品方向（v2）：超越 UU 远程的跨平台远控

最后更新：2026-10-17

> 本文是新方向的总纲。旧的「复刻并互通官方 UU」是手段，不是目的；
> 从现在起，**主产品是我们自己的协议与网络**，与官方互通退居为可选的兼容能力。

## 1. 定位

一个**开源、原生、跨平台（Windows + Linux，双端对等）**的远程桌面系统，
在三个方向上超过官方 UU 远程：

1. **多控一**：多台控制端同时连接同一台被控设备。
2. **自主网络**：不依赖网易的中间网络——局域网直连、P2P 打洞、自托管中继。
3. **体验超越**：无撕裂（垂直同步）、低延迟、简洁美观的 UI。

两端都做：既能**被控**（host）也能**主控**（controller），Windows 与 Linux 一视同仁。

### 关键决策（已定，2026-10-17）

- **与官方 UU 互通**：保留，但隔离为可选 `interop` feature；主产品是 native。
- **P2P 底座**：复用 **WebRTC ICE/DTLS-SRTP**（webrtc-rs），自建信令/STUN/TURN；
  不自己造 NAT 穿透。
- **多控一输入**：默认**多人同时可操作**（可再切「一控多观」/只看）。

### 当前版本（V1）范围

- **主控端跑在 Linux，连接官方 Windows UU 被控端**（即 interop 模式）。这是本阶段
  要打磨好的交付物：稳定画面、键鼠可用、硬件解码、无撕裂、简洁 UI。
- native 自有协议（own host + own client）作为**后续主线**（路线图 M1+）。
- 形态上对标 **Sunshine（被控端）+ Moonlight（主控端）** 的组合，拿来主义、少走弯路。

### 痛点对照：UU 与 Sunshine+Moonlight（我们要两者兼得）

长期用 S/M 的真实痛点与 UU 的强项，正好互补。我们的目标是**同时拿下两边**：

| 能力 | UU 远程 | Sunshine+Moonlight | 我们 |
|---|---|---|---|
| 多显示器串流选择 | ✅ | ❌（痛点） | **必做** |
| 鼠标自由切回本机（指针捕获/释放） | ✅ | ❌（痛点） | **必做** |
| 剪贴板 | ✅ | ❌（痛点） | **必做** |
| 自定义码率 | ❌ | ✅ | **必做** |
| 硬件编码参数可调（NVENC/QSV/VAAPI/AMF） | ❌ | ✅ | **必做** |
| 输入 IP 直连 | ❌ | ✅ | **必做** |
| 手柄输入 | 部分 | ✅ | **必做** |
| 低延迟 / 无撕裂（垂直同步） | ❌（撕裂） | ✅（部分） | **必做** |
| 多控一（多台控制端连同一被控） | ❌ | 部分 | **特色** |
| 按连接者授权键鼠/手柄/剪贴板（Parsec 式） | ❌ | 部分 | **必做** |
| 开源自托管网络（直连/P2P/自建中继） | ❌ | 部分 | **特色** |
| 简洁美观的 UI | ✅ | ❌（界面朴素） | **必做** |

由此得到**功能清单（差异化的核心）**：
多显示器选择、鼠标自由切换、剪贴板、自定义码率、编码参数可调、输入 IP 直连、
手柄、无撕裂、多控一、自托管网络、好看好用的 UI。

## 2. 三大支柱（北极星）

### P1 · 多设备连接同一设备（多控一）

官方 UU 一台被控端同一时刻只接受一个控制会话。我们要支持：

- **被控端会话管理器**：一个 host 进程并发维护 N 个控制器连接。
- **媒体分发**：一次采集、一次编码、fan-out 给所有控制器；后续可按各控制器
  的带宽/分辨率分别编码（多档/SVC）。
- **输入仲裁与权限**：默认**多人同时可操作**；每个连接可**单独授权**键盘 / 鼠标 /
  手柄 / 剪贴板（类似 Parsec 的「是否允许该连接者使用键鼠」开关），也可切
  「控制权令牌 / 一控多观 / 只看」；支持会话上限与会话列表管理（踢人、移交控制权）。
- 被控端 UI 显示当前会话、谁在控制、可踢人/移交控制权。

### P2 · 自主网络（摆脱官方中间网络）

三条连接路径，由近到远：

1. **局域网直连**：主控端手动输入 `IP:端口`（或扫二维码/ID），直接连上。
   完全离线，不需要任何服务器。host 默认监听固定端口。
2. **P2P 打洞**：自建**轻量 rendezvous（信令）服务器** + STUN，双方交换候选后
   走 ICE 打洞；用于跨网段/公网。
3. **自托管中继**：打洞失败时回退到自建 TURN/中继（自己的服务器，不是网易的）。

配套：
- **设备寻址**：短 ID + 一次性口令（类似「设备码 + 验证码」），由 rendezvous 解析；
  或纯离线直接用 IP:端口。
- **可选发现**：局域网 mDNS/Broadcast 自动发现同网段 host。
- 目标是**整套服务器都由我们自己部署**，UU 的服务器只在与官方设备互通时才用。

### P3 · 体验超越

- **无撕裂 / 垂直同步**：渲染按 vblank 呈现（可开关，默认开）。
- **低延迟**：解码到渲染走 GPU 纹理直显、零拷贝；帧节流对齐刷新率。
- **简洁美观的 UI**：重新设计；管理面板与串流窗口分离；深/浅色、多语言。
- **画质**：H.264 / H.265（后续 AV1）可选，码率自适应。
- 其他逐步补齐：音频、剪贴板、文件传输、多屏、端口映射、终端等。

## 3. 两种运行模式

| 模式 | 说明 | 依赖 |
|---|---|---|
| **native（主）** | 自研协议 + 自主网络，host 与 controller 都是我们 | 无（局域网）/ 自建 rendezvous+STUN+TURN |
| **interop（兼容）** | 连接/被官方 UU 客户端连接 | 网易 API/信令（现有着色代码保留，隔离为 feature） |

interop 里的鉴权、CONTROL 输入协议、视频解码等成果**全部保留**，作为兼容模式，
也作为 native 协议设计的参考。

## 4. 架构

```
                       ┌───────────────────────────┐
                       │  渲染窗口 (native, vsync)  │
   controller         ├───────────────────────────┤
   (Windows/Linux) ── │  解码 (ffmpeg 软/硬)       │
                       │  输入采集 → 发送            │
                       └──────────┬────────────────┘
                                  │  native 协议
        ┌─────────────────────────┼─────────────────────────┐
        │                         │                         │
  局域网直连(TCP/UDP)        P2P (ICE/DTLS-SRTP)      自托管中继(TURN)
        │                         │                         │
        └─────────────────────────┼─────────────────────────┘
                                  │  可选：rendezvous(信令)+STUN
                       ┌──────────┴────────────────┐
   host                │  会话管理器 (N 个控制器)   │
   (Windows/Linux) ── │  采集 → 编码 → fan-out      │
                       │  输入仲裁 → 注入            │
                       └───────────────────────────┘
```

| `uu-media` | 编解码抽象、像素转换 | 已有，待加硬件后端 |
| `uu-capture` | 采集（Win WGC/DXGI，Linux PipeWire/X11） | 占位，待实现 |
| `uu-input` | 注入（Win SendInput，Linux uinput/XTest） | 有雏形 |
| `uu-net` | 传输：direct / p2p / relay | **新增** |

| `uu-host` | 被控端：会话管理 + 采集编码 + 注入 | **新增** |
| uu-cli / uu-gui | 主控端 CLI / 图形客户端 + 被控端 UI | 已有，待重做 UI |
| interop | 与官方 UU 互通（现 `sign/api/signal/socketio/control_wire/controller`） | 已有，隔离为 feature |

## 5. 技术选型与取舍

- **传输：优先复用 WebRTC（ICE + DTLS-SRTP）**，自建信令/STUN/TURN。
  理由：ICE 已经实现了 STUN 打洞与候选交换，DTLS-SRTP 实现媒体加密，能省掉
  一大块最容易出错的网络工作；而服务器全是我们自己的，仍然满足「自主网络」。
  KCP/QUIC 自研传输只在 WebRTC 不能满足时再考虑（例如极低延迟游戏场景）。
- **局域网直连**：不引入 WebRTC 的复杂性，用我们自己的 TCP（控制）+ UDP（媒体）
  简单封包即可，先跑通最小闭环。
- **编解码：统一走 FFmpeg**（子进程或 libav），软件与硬件（NVENC/QSV/VAAPI/
  D3D11VA）一套抽象；OpenH264 保留为纯软件回退。
- **采集/注入**：收敛在 `Capture` / `InputInjector` 两个 trait 后面。
- **UI**：串流窗口用**原生渲染**（低延迟 + vsync）；管理壳近期用 egui 重做主题
  与布局，后期可评估 Tauri（Web UI）承载管理面板。
- **许可**：保持 MIT OR Apache-2.0；参考其它项目时只用**协议事实**，不复制
  GPL-3.0 代码（如 `uu-remote-linux`）。

## 7. 现有代码如何复用 / 重构 / 归档

- **保留并继续用**：`uu-media`（编解码/转换）、`uu-capture`、`uu-input`、
  `uu-proto` 的通用帧/分片、`uu-gui` 骨架。
- **隔离为 `interop` feature**：`sign`、`api`、`signal`、`socketio`、`control_wire`、
  以及 controller 里的 UU 专用逻辑（room/join、CONTROL 输入、iceServers）。
- **已归档**：`pck/turn/stun/sdp`（TURN/PCK 旧路线，见 `archive/protocol-legacy/`）。
- **新增**：native 协议、`uu-net`、`uu-signal`、`uu-host`。
- 参考 `VallierDev/uu-remote-linux` 的被控端实现（采集/编码/注册/输入映射思路）
  可以少走弯路，但以我们的 native 协议与三支柱为准。

## 8. 风险

- **自建信令/NAT 穿透**是真难点（对称 NAT 必须靠中继兜底）。
- **多控一的编码成本**：单编码 fan-out 只能满足「看同一画面」；差异化画质要 N 路编码。
- **跨平台采集/注入**（Win WGC/DXGI、Linux PipeWire/portal）工作量不小。
- **无撕裂渲染**在不同平台/合成器行为不一，需要实机验证。
- **合规**：interop 只用于互操作；native 模式不依赖任何网易资产。

## 9. 借鉴 Sunshine / Moonlight

形态对标：**Sunshine = 被控端**，**Moonlight = 主控端**。可吸收的方向（实现时逐项核对）：

- **Sunshine（被控端）**
  - 编码后端抽象：NVENC / QSV / VAAPI / AMF / 软件，H.264 / HEVC / AV1，HDR。
  - 采集后端：Windows DXGI Desktop Duplication；Linux KMS/DRM 或 PipeWire。
  - 输入注入：Windows `SendInput` + **ViGEmBus 虚拟手柄**；Linux `uinput`。
  - Web 配置界面、多会话管理、低延迟选项与自适应码率。
- **Moonlight（主控端）**
  - **解码 → GPU 纹理 → vsync 呈现**的低延迟渲染管线（我们的 P3 无撕裂）。
  - 手柄/键鼠映射；多主机管理；**控制流与音视频流分离**的协议设计。
- 拟吸收进 native 协议：独立**控制通道** + 独立**媒体流**；**手柄**与**多控一**
  从设计之初就作为一等公民，而不是事后补。
- 注：以上为可借鉴的工程方向，具体能力以各自项目最新文档/源码为准，落地前再核实。

## 10. 解码后端（进程内优先）

- **默认：进程内 OpenH264 软件解码**。实测 1080p **~2.9 ms/帧（约 340fps 余量）**，
  60fps 毫无压力。
- **外部 ffmpeg 子进程方案已废弃**（见 `archive/ffmpeg-subprocess/`）：进程间管道
  缓冲带来高延迟，实测只有 5~10fps、操作不跟手，不适合实时串流。**不要**用它。
- **硬件解码**要做成**进程内**后端：
  - Windows：Media Foundation（MFT/DXVA，可 D3D11 纹理直供渲染）。
  - Linux：VA-API（libva / ffmpeg 库，非子进程）。
  - 仅 4K/HEVC/低端 CPU 才需要；1080p H.264 软件已足够。
